## A3 归档服务与恢复验证（2026-09-29）

- `GameArchiveService` 的同步确认与 worker 使用同一独立待办、UUID owner 租约和精确 ACK；只补写已提交事实，不调用 AI、不再次应用道具/HP/回合效果。
- MySQL 在同一事务中写入连续档案并补齐进度，按 room→capability→timeline 的锁顺序检查活动时间线和 revision；缺口/哈希冲突回滚整个事务。控制操作隔离期间只排空原事实，不修复当前进度；活动分支已更换则拒绝旧归档 ACK。
- 旧单人/多人的单调进度 SQL 增加能力状态排除条件；新模式结果走归档确认路径，后续存读档不能被迟到的旧补偿覆盖。
- 已确认提交在 MySQL、ACK 或交付元数据读取失败时保留 pending/recovering；精确重试 ACK 不增加 deadline。结果只使用当前 generation/turn 对应的权威计时器，pending 不推送 turn_start。
- worker 默认 1 秒轮询、32 房间批次、5 秒操作预算、30 秒租约、1—30 秒指数退避、7 秒关闭等待；租约每三分之一时长续期，领取/续期移动队列到租约到期时刻，避免忙房间占满批次。尝试次数和下次重试保存在 Redis，重启不重置。
- 不可恢复的缺口、哈希/分支冲突或损坏记录设置 blocked、保留原待办并退出轮询队列；旧 owner 不能隔离/删除新 owner 待办。关闭会停止领取、取消在途工作并有界等待；未完成确认依赖保留待办和租约到期接管。

- start 日志保留一次生成的完整开场及快照。Redis provisional 和控制门禁先阻止行动，单人持久化开局/多人房间版本与阵容事务成功后才激活；完成分支发布后将 opening 放入归档待办，归档前不接受第一行动。明确失败会 abort 并精确清理 provisional，不生成正式开场；不确定结果保留日志，恢复不调用 AI。已有持久化 start 意图的多人房间在调用 AI 前拒绝重复开局，不因短租约失效或关闭新建开关而重新生成；两种开关取值均有单元测试。
- V3 envelope 保留模式原有 V1/V2 的运行态语义，摘要和近期消息只存原列。严格校验必需字段、未知字段/版本、模式、阵容、房间、SQL 引用、水位和历史完整标志；不保存 generation、deadline、行动租约或可变归档元数据。摘要捕获来源字段为 `opening/runtime/legacy`。

- load 以请求 UUID 去重，稳定生成目标 timeline/generation；在 MySQL 原子准备目标、快照哈希及控制意图，再 Redis 栅栏、排空旧待办、替换为 paused、原子发布精确进度和分支、精确解除门禁。V3 继承保存前缀；V1/V2 建立不完整恢复根，在位置 0 保存一份 legacy_baseline。重复操作不新建分支、不恢复旧计时器。

- end 在控制栅栏捕获精确进度，排空待办后持久化 ended，最后按 token 清理普通运行态。档案、控制日志、确认回执及独立队列不进入普通 TTL/清理；旧操作不能清理新分支。

## A5 协议与最小界面（2026-09-30）

- 新增 `GET /api/v1/games/{roomId}/memory-status`：单人房主或多人有效成员可读，旧房间返回 `disabled`；新模式返回 `ready/pending/recovering/blocked/ended`、当前 timeline/generation 和归档水位，不返回历史正文。无权访问统一为 404，状态不可用为 503。服务端不把缺失/损坏记忆元数据降级成旧模式。
