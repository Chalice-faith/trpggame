## 3. 当前接口与状态边界

### 已开放接口

- `POST /api/v1/games/solo/start`
  - JWT 鉴权；
  - 校验用户拥有且已解析完成的剧本及角色；
  - MySQL 创建等待房间和玩家，调用 Python 生成开场，初始化 Redis 后激活房间；
  - AI、Redis 或状态切换失败时执行补偿并结束房间。
- `POST /api/v1/games/:roomId/action`
  - 请求体：`request_id`、`expected_turn`、`action_text`；
  - 当前采用同步 REST 响应，不是 SSE/WebSocket 流式输出；
  - 通过 UUID、请求指纹和预期回合实现幂等与 CAS；
  - Python 返回的状态调用由 Go 白名单解释后统一写入 Redis；
  - 返回叙事、骰子结果、结构化效果和最新回合号。

### 已实现但未开放接口

- 手动存档 Service：
  - 仅允许房主保存 `playing` 或 `paused` 单人房间；
  - 要求 MySQL 与 Redis 房间状态一致；
  - 原子捕获 Redis 运行态，将版本化快照、摘要和最近消息分别写入 `game_saves`；
  - HTTP Handler、路由错误映射仍未实现，因此现有 `/games/:roomId/save` 仍是占位响应。

### 持久化边界

- MySQL 保存房间元数据、玩家关系和游戏存档，是持久化权威。
- Redis 保存房间实时状态、回合、玩家属性、道具、Buff、摘要、最近消息及行动幂等结果。
- 快照不持久化行动幂等缓存；恢复时会清空缓存，避免跨时间线重放旧响应。
- `trigger_event` 当前只经过严格校验并随行动结果返回，不写 MySQL；关键事件表按规划属于 Phase 3 的 `012_create_key_events.sql`。
