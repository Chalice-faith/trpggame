## 1. 本块要交付什么

建立单人和多人共用的“已提交剧情事实来源”，让下一块的关键事件、摘要及语义检索能够区分：这件事是否真的提交、属于哪个房间、在当前读档分支是否仍然发生过。

完成后的行为：

1. 成功开场、正式行动、主动跳过和超时跳过各有唯一持久化记录；失败生成和临时流式片段不成为事实。
2. 普通暂停/恢复不切断历史；读档建立新分支，不召回被撤销的未来。
3. 进程重启或重复请求只补写已提交结果，不再次调用 AI 或再次扣除行动槽。
4. 存档记录自己的时间线和已持久化位置；不同分支走到相同回合时可以分别自动存档。
5. MySQL 归档失败时明确提示“已提交、正在归档”，阻止继续推进；恢复后可继续，不伪装成行动未发生。

本块不实现关键事件提取/列表、摘要更新、embedding、Milvus 历史检索、自定义角色、投票、语音、历史回放编辑器或依靠事件重建全部运行态的引擎。`trigger_event` 只作为已校验行动效果的一部分归档，事件独立表留给 M3.1-B。

## 4. 核心不变量与时间线模型

### 4.1 四类标识

| 标识 | 职责 | 生命周期 |
|---|---|---|
| `generation` | 使旧 AI 请求、控制操作和 worker 失效 | 沿用暂停/读档等操作的世代隔离 |
| `timeline_id` | 表示一条剧情分支，服务端生成 UUID | 暂停/恢复不变，成功读档创建新值 |
| `position` | 分支路径上的正式提交位置 | 开场/行动/跳过等提交递增；不依赖回合或广播 seq |
| `commit_id` / `request_id` | 分别标识正式记录与客户端意图 | 提交 ID 在重试期间稳定；请求 ID 复用且内容不同必须冲突 |

不变量：同一时间线位置最多一条正式记录；相同提交 ID 的内容不可变化；运行态 head 不小于持久化连续水位；只有当前分支允许的新提交可以改变运行态。

同一房间每次最多有一条未确认归档的剧情提交。初版用此上限简化恢复并限制积压；不得通过每次换一个 request_id 绕过门禁。

### 4.2 位置与祖先可见性

- 新游戏根分支从位置 1 的正式开场开始，初始已归档水位为 0。
- 从分支 T0 的位置 20 读档生成 T1：T1 的起始水位为 20，新记录从 21 开始；T0 的 21—30 不进入 T1 上下文。
- 再从 T1 的位置 23 创建 T2：可见 T0 的 1—20、T1 的 21—23，以及 T2 新增的 24 起记录。
- 若加载的是 T0 的位置 10，则新分支的父级是存档所指向的 T0，不是读档前正在玩的 T2。
- 查询返回的是按路径排列的有界片段：每层只取本分支起点之后、继承上限之前的记录；祖先上限逐层收紧。验证同房间、无环、父级水位合法，异常时拒绝读取，不能退化成全房间历史。
- 初版采用迭代查询而非无限递归；建议祖先深度上限 256，超限明确拒绝继续分叉并记录告警，后续再设计压平，不静默漏历史。

本块提供 Go 内部的 `ListVisibleRecords` 能力并测试分页；页面事件列表留给 B。分页游标绑定房间、当前 timeline 与各段水位，读档后旧游标失效；不能让客户端自行传入任意祖先范围。

### 4.3 哪些内容成为历史

正式记录类型为 `opening`、`action`、`skip_manual`、`skip_timeout`；另有明确标注为恢复基线、非原始行动的 `legacy_baseline`。为后续 `vote_result` 保留扩展机制，本块不产生该类型。

记录包含经过服务端校验的用户行动、最终叙事、骰子、归一化效果、行动者及提交前后回合信息。跳过记录允许没有 AI 叙事。流式 chunk、AI 调用失败、提交 CAS 失败、未激活的临时开场都不生成正式记录。

客户端取消或暂停若发生在原子提交之前，结果无效；若提交已发生，则必须保留该事实并完成归档，不能因为响应断开而删除它。

## 5. 数据与迁移设计

以下字段、文件名和编号是待冻结方案，不是已存在的模型或迁移。当前 manifest 到 017；实现时重新检查下一个可用编号，禁止修改 001—017。

### 5.1 建议实体

| 实体 | 关键字段 | 约束与用途 |
|---|---|---|
| `game_memory_states` | `room_id`、`active_timeline_id`、`status`、`revision`、`active_operation_id` | 每房间一行；存在该行才表示启用新模式；status 为 initializing/ready/recovering/blocked/ended，非房间主状态 |
| `game_timelines` | `id`、`room_id`、`parent_id`、`fork_position`、`durable_position`、`origin_save_id`、`history_complete`、`status` | 父关系及分叉点不可变；连续归档水位按分支维护；prepared/active/aborted 用于控制操作恢复 |
| `game_action_records` | `commit_id`、`room_id`、`timeline_id`、`position`、`kind`、`actor_id`、`request_id`、`fingerprint`、`source_generation/revision`、`turn_before/after`、`round_before/after`、`payload_version`、`payload`、`payload_hash`、时间戳 | 唯一 commit_id；唯一 `(room_id,timeline_id,position)`；客户端请求在房间内去重，服务端开场/跳过使用独立命名空间 |
| `game_memory_operations` | `operation_id`、`room_id`、`kind`、`fingerprint`、源 timeline/generation、目标 timeline/save、`phase`、目标快照/哈希、重试信息 | start/load/end 等跨存储操作的持久化日志；同房间由 memory_states CAS 约束一个未完成控制操作 |
| `game_saves` 扩展 | 可空 `timeline_id`、可空 `memory_position`、新的自动存档去重范围 | 旧行保持 NULL；新存档关系字段与 JSON 元数据必须一致 |

采用应用层关系校验，不新增数据库外键。时间统一 UTC；UUID 规范化后比较；哈希按固定字段和序列化版本生成，排除请求耗时等易变信息。不得用忽略所有冲突的 INSERT 代替“读回并核对同一内容”。

关键索引：历史按 `(room_id,timeline_id,position)` 分页；操作按未完成状态/下次重试时间扫描；房间内请求按请求命名空间与 request_id 唯一。记录正文/完整玩家状态不写到普通日志。

建议迁移拆为：018 时间线及房间记忆状态、019 正式记录及恢复操作、020 存档元数据和唯一键调整。每个文件必须配空库和 017 升级测试；实际编号以实现时 manifest 为准。

### 5.2 自动存档唯一性

保留原 `auto_round_number` 生成列及当前自动存档周期：单人每 10 个行动回合，多人每 5 个完整轮次。

建议新增生成范围 `auto_timeline_scope`：自动存档取实际 timeline UUID，旧存档取保留值 `legacy`；手动存档取 NULL。唯一键改为 `(room_id, auto_timeline_scope, auto_round_number)`。

- 旧自动存档仍按房间/回合去重，旧手动存档仍可在同一回合创建多份。
- T0 和 T1 在同一轮次可各保留一份自动存档，同分支重复补写仍只生成一份。
- 新模式写入时禁止 NULL timeline；新旧 JSON、房间和位置必须一致。
- 重复自动存档要核对存档位置与内容哈希，不能仅凭“唯一键冲突”宣布成功。
- 新模式 Redis 自动存档待办使用 timeline/position/自动轮次组成的身份；先确认该水位已归档，再写自动存档并精确 ACK。
- 迁移须验证旧唯一索引移除与新索引建立的全过程，保留全部原始存档；不能通过删除旧行解决冲突。

### 5.3 暂不创建索引任务表

总体规划中的 `memory_index_jobs` 属于 C 的实际索引交付。A 先提供不可变、可枚举的事实源；B/C 上线时扫描已有档案补种任务，并将新增任务与事实写入接到同一 MySQL 事务，使用唯一来源/version 键和追平水位避免切换漏项。

因此 A 不创建永远无人消费的向量任务，也不调用 Python。后续消费者不能依赖 Redis 有界回放作为补种来源。

## 6. Redis 提交与归档恢复

### 6.1 新模式元数据和待办

建议使用独立的房间记忆元数据、待归档 payload、待处理房间队列和归档租约。命名在 A0 冻结，避免直接挂进当前 `runtimeKeys` / `soloRuntimeCleanupKeys` 的通用删除和过期列表。

- 运行态携带 `timeline_id`、`head_position`、`durable_position`、`archive_state`、`control_operation_id`。
- 未确认的归档 payload 和队列不设置普通 24 小时运行态 TTL；单条正文建议上限 1 MiB，超限在提交前拒绝，不截断后冒充完整档案。
- 租约有短 TTL 和 owner token；ACK/释放必须核对 token、commit_id 和哈希。租约过期只能重新领取，不能删除 payload。
- Lua 对新增键类型、负载大小、全部效果先校验，再写运行态/档案待办/幂等结果/队列；验证失败不得已经扣血或推进回合。
- 源运行态过期后，worker 仍可把待办写入正确房间/分支，但不得凭一条行动自动重建整局运行态。

Lua 串行执行不等于发生运行错误时自动回滚。写入阶段异常或响应丢失必须核对 commit_id、head 与待办，不能直接解释为“没有提交”；状态无法确认时进入恢复门禁。A2 的测试要区分预校验拒绝、脚本运行错误和网络响应丢失。

### 6.2 正式行动处理顺序

1. 校验成员权限、房间模式、请求幂等和客户端预期 timeline/generation/turn。新模式门禁未 ready 时不调用 AI。
2. 多人继续抢占当前行动租约；单人保留现有提交 CAS，同时增加提交时归档门禁。并发单人推理最多一个能正式提交，本块不声称解决所有重复推理计费。
3. 接收流式片段但不归档；完整结果经现有效果/骰子校验后构建稳定的提交 payload。
4. Redis 原子提交再次校验世代、时间线、回合、租约和无待办，同时更新状态、分配 position、缓存结果并登记归档待办。设置 archive_state=pending，不立即开放下一行动。
5. 请求线程尝试限时归档：MySQL 事务锁定分支，检查期望连续位置，插入档案并推进 durable_position；已有同一记录仅在哈希相同时视为幂等成功。
6. Redis 精确确认归档；只有待办仍匹配且没有控制操作/暂停时才解除门禁。普通后续推进、MySQL 进度同步、自动存档和实时通知均检查当前时间线，旧补偿不能覆盖读档后的进度。
7. MySQL/Redis ACK 失败由后台 worker 继续；响应说明已提交且归档待完成。客户端保留同一 request_id，不以新 ID 重做行动。

连续水位只能从 p 推到 p+1，不能用最大 position 跳过缺口。旧 generation 的已提交待办即使在暂停后到达仍要归档；世代失效只能否决尚未提交的工作。

最终叙事/效果内容在提交后不可修改；deadline 和当前归档状态是交付元数据，不纳入不可变事实哈希。幂等重放组合固定内容与当前确认状态，禁止重新应用效果或重放过期 `turn_start`。

### 6.3 deadline 与玩家反馈

新模式在 pending/recovering 时没有可执行的行动 deadline，且 deadline worker 不能跳过玩家。实时状态校验需允许“playing + archive pending + 无 deadline/行动租约”，不能误报快照损坏。

归档确认后，若仍是当前 playing 分支，才一次性为当前行动者设置完整时限并登记队列；若房间已 paused/ended 或发生读档，则 ACK 不开启计时器。重复确认不能延长时间。恢复后的快照、缓存响应和 `turn_start` 使用同一最终 deadline。

界面只补最小状态：归档中、恢复中、需人工处理、已就绪；提交结果不确定时通过状态查询/原请求重试确认。不能同时显示“行动失败，请重做”和已经更新的 HP/回合。

### 6.4 Worker 与故障范围

建议独立 `GameArchiveWorker`，覆盖单人和多人，不让一个 MySQL 故障房间阻塞所有 deadline。初始参数建议：每秒扫描、批量 32 房间、单次写入预算 5 秒、30 秒租约并可续租、指数退避上限 30 秒；通过配置和测试调整，不硬编码在前端。

进程退出时停止领取新任务、等待有界进行中任务；未完成 payload 保留。多个 Go 实例共享队列，依靠唯一键、事务和精确 ACK 收敛，不承诺任务只投递一次。

启用前显式评估 Redis AOF、数据卷和内存淘汰策略，建议未归档数据不可被淘汰。即使启用 AOF，也不承诺 Redis 与 MySQL 跨存储、断电或磁盘损坏下零丢失。若 Redis 已提交记录丢失且 MySQL 无对应档案，房间进入 blocked，保全现存数据并使用经过确认的存档恢复；不能凭客户端叙事补造事实。

上述阻断针对可检测的不一致；若 Redis 回退到一个旧但自洽的快照，系统未必能证明最后一次未归档提交曾发生，不能承诺检测所有丢失。若此风险不可接受，须在 A-D03 确认前改用更强的提交权威/持久化方案，而不是靠增加重试声称解决。

## 7. 开场、生命周期与读档分支

### 7.1 开场

新模式使用 start 操作日志保留服务端生成的 generation、root timeline 和待激活快照；开场正文在 AI 完整返回后记录为待激活数据，尚不能被历史查询读取。

多人在当前 `InitializeMultiplayerRoom` provisional 阶段不发布历史；只有房间持久化开局成功、Redis 激活核对成功后，才将 opening 纳入正式待归档。单人也增加等价的未激活门禁，避免 Redis 初始化成功、MySQL 开局失败却留下正式开场。

激活不确定时通过 start operation、房间状态和 Redis token 核对：已激活则只补归档；仍是合法 provisional 则恢复激活或保持安全暂停；明确失败则 abort。恢复不能自动再次调用 AI，也不能把成功开局的正文当临时数据删掉。开场归档完成前不接受第一行动。

### 7.2 各操作规则

| 操作 | 时间线规则 | 与待归档的协调 |
|---|---|---|
| 暂停 | timeline 不变，继续使用 generation 使在途工作失效 | 允许安全暂停；已提交待办继续归档，不被取消 |
| 恢复 | timeline 不变 | 先确认无待办/未完成控制操作，再允许行动并恢复 deadline |
| 手动存档 | 保存当前 timeline 和精确 position，不分叉 | 先暂停/建立控制栅栏，待水位追平后原子捕获；建议新模式单人也与多人一致保持 paused |
| 自动存档 | 使用行动提交时捕获的边界快照 | 归档水位确认后写入，不能用 worker 执行时的最新快照代替 |
| 读档 | 从存档引用创建新分支，保持 paused | 先暂停、排空旧归档和自动存档，再做可恢复分支替换 |
| 结束 | 保留已提交历史，关闭继续写入 | 先暂停并完成待办，再确认结束与清理；故障时不宣称结束完成 |

存档、读档、结束必须在最终写入/清理前再次校验控制 token。`generation` 轮换不能清掉未归档 payload；状态已经 ended 时重试仍要检查未完成收尾。

### 7.3 读档可恢复步骤

1. 鉴权并校验房间/存档归属、格式、成员阵容、timeline 与保存水位；无权限请求不得获知历史正文。
2. 以客户端 `request_id` 在 MySQL 同一事务中建立 load operation、已校验目标快照及 prepared 分支，按来源 revision CAS 占用房间控制槽；prepared 分支尚不可读。同 ID 同请求复用原操作；不同内容冲突。前端重试复用 ID，另一次有意读档使用新 ID。
3. Redis 原子设置控制 token、暂停并轮换 generation，隔离在途提交。若已有行动先提交，则以栅栏捕获的 head 为准排空它，不能漏掉这条历史。
4. 排空旧分支归档及自动存档；失败保持 paused/recovering，禁止继续恢复、另一次读档或结束清理。
5. 核对持久化操作的 source timeline、token、目标分支与完整快照哈希。新分支的继承水位来自存档，不来自当前回合。A4 将目标准备提前到第 2 步，保证 Redis 栅栏前崩溃也有可恢复的意图；期间先提交的行动由第 3—4 步排空。
6. Redis 比较 source timeline/generation/control token 后原子恢复新快照，记录 operation_id；房间仍 paused，新 generation 与新 timeline 生效。
7. MySQL 事务将操作标记 applied，更新房间活动 timeline 和精确游戏进度；最后精确解除 Redis 控制门禁并推送权威快照。旧阶段的单调进度补偿不能在此之后覆盖加载值。

崩溃恢复判定：Redis 已带相同 operation_id/目标快照，则只完成 MySQL/解锁；仍是原来源且 token 匹配，则可继续应用；两边不匹配则 blocked，禁止盲目再次 Restore。若运行态完全丢失，只能依据持久化的目标快照及控制日志核对后恢复 paused，不自动继续游戏。

控制槽过期不等于操作完成：后台必须检查持久化日志后恢复/中止，不能因租约到期直接允许第二个 load。A0 先为上述每个切点建立故障测试，再接入真实服务流程。

## 8. 新旧存档与旧房间兼容

### 8.1 格式方案

建议新增持久化 envelope：`schema_version=3`、`mode=solo|multiplayer`、模式对应的 `runtime`、`memory`。`memory` 包含 timeline_id、保存 position、history_complete 和摘要来源标识；具体字段名在 A0 冻结。

- `runtime` 复用 V1/V2 的角色、回合、道具、Buff 等语义；不把外层 schema_version 直接写入所有 Redis/WS 的 `version`。
- 摘要和近期消息继续使用 `game_saves` 现有列，不多存一份容易分叉的正文；保存时同时捕获并校验，快照哈希覆盖这些内容。
- 解码先识别 envelope 或旧 version，再交给相应严格 decoder；未知版本、非法混合模式或元数据不一致显式拒绝，不改成宽松反序列化。
- 读档不恢复旧行动租约、旧 deadline 或旧 generation；多人继续校验冻结成员、角色、行动顺序。

### 8.2 兼容矩阵

| 场景 | 方案 |
|---|---|
| 未启用记忆的旧活动房间 | 保持原运行态/存档路径；本块不批量原地升级 |
| 新启用房间的新存档 | 写 V3，必须引用已归档水位；读档正常分叉 |
| 新模式房间加载同房间旧 V1/V2 | 建立无父级的恢复根分支，位置 0 保存 `legacy_baseline`；后续正式提交从 1 开始 |
| 旧活动房间希望启用新模式 | 本块不提供自动转换入口；后续独立迁移方案，不偷偷改变进行中的房间 |
| 旧存档没有完整历史 | 只继承存档实际含有的状态、摘要和近期消息；`history_complete=false`、摘要来源为 legacy/unknown |
| 新模式元数据表或 Redis 元数据缺失 | 按损坏/恢复流程处理；不能自动退回旧路径继续写 |
| 关闭新房间启用开关 | 不再为新房间启用；已启用房间仍使用新协议与恢复逻辑 |

旧存档原 JSON 不改写、不从当前房间未来历史补齐。加载旧格式的适配器要独立测试，即使第一批新房间没有历史旧存档，也不能虚构“已在真实迁移场景验证”。

新增房间默认是否启用由服务端配置决定，并持久化到房间能力状态；建议首次交付默认关闭，在专用测试环境开启。所有实例升级到理解新模式的版本后才能开启，旧实例不能继续处理新模式房间。

## 9. 接口、安全与客户端最小改动

本块不开放完整行动正文检索 API；以下是待实现契约，不是当前可调用接口。

- 新增 `GET /api/v1/games/{roomId}/archive-status`，统一供单人房主/多人有效冻结成员读取。返回 enabled、timeline_id、generation、head_position、durable_position、archive_state、当前控制操作标识和可重试性，不返回全部历史或内部错误堆栈。
- 状态查询可带本人行动的 request_id，返回该请求的未查到/待归档/已归档/已属旧分支状态及 commit_id。未查到不能在 Redis/MySQL 读取失败时伪装返回；原行动接口可只读重放已提交结果，但旧分支结果不重新广播为当前事件，也不自动重开计时器。
- 新模式行动/跳过请求增加预期 timeline_id 与 generation，REST 和游戏 WS 同步校验；缺失或过期时拒绝并提示刷新。旧模式继续接受原契约。服务端不能信任请求中的分支归属。
- 读档增加 request_id；新模式必须提供，旧模式兼容原 `save_id` 请求。客户端断网重试保持该 ID，状态确认后才丢弃。
- 行动成功内容增加可选归档状态/位置。若 Redis 已提交而归档暂未完成，返回可识别的 pending 结果和状态查询入口，不作为 AI 失败重试；提交是否成功无法确认时明确 unknown 并查询原 request_id。
- WS 增加 `archive_status` 状态事件，沿用现有房间 seq；断线后以状态接口/快照为准，丢广播不影响档案正确性。客户端按请求/提交 ID 去重叙事和效果。
- 新增错误语义：归档未就绪、分支已变化、存档引用损坏、控制操作冲突；具体数值在 A0 核对已有 13xx/19xx 后分配，Go/OpenAPI/WS/Vue 同步。

归档文本属于不可信游戏数据，仅在后续受控上下文中使用，不得提升为系统指令。查询和重试必须再次鉴权；日志仅记录 room/timeline/commit/operation ID、耗时、错误分类。档案关联删除由明确的数据删除操作执行，不与“结束游戏”“删除某个存档”混淆。

前端只修改单人/多人游戏页、API 类型、WS 合并和状态提示，不做事件时间轴或全站视觉改版。待归档时禁用行动/跳过/恢复等依赖持久化的操作，但保留安全暂停和查看恢复状态的入口。

## 14. A1 冻结契约与交付

- 实际迁移为 `018_create_game_memory_timelines.sql`、`019_create_game_action_records.sql`、`020_extend_game_saves_memory.sql`，001—017 未修改；多表 CREATE 分条执行，继续禁用连接的 multipleStatements。

- 请求命名空间冻结为 `client`（行动/主动跳过）、`opening`、`timeout`、`legacy`。UUID 在封存前规范化；commit、位置、请求唯一约束发生冲突时明确拒绝，禁止吞冲突。
- `payload_version=1` 的 SHA-256 覆盖记录不可变字段与规范化 JSON，排除实际创建时间和哈希本身；大整数使用 JSON Number，正文上限 1 MiB。分支祖先最多 256 层，分页最多 100 条。
- 控制阶段为 `prepared → redis_applied → completed`；prepared 可 aborted，prepared/redis_applied 可 blocked。房间行锁串行化控制意图；阶段完成在同一事务发布目标分支。Repository 本身不证明 Redis 已切换，必须由 A4 校验运行态 token 后调用。
- 新存档持久化元数据为 `timeline_id`、`memory_position`；envelope 采用 `schema_version=3`、`mode`、`runtime`、`memory.timeline_id/position/history_complete`。A1 只校验关系元数据与 JSON 一致、归档水位和内容哈希；完整 V3 严格 decoder/摘要来源字段在 A4 完成前不能启用。
- 可见分页游标为 Go 内部不透明对象，绑定房间/当前时间线/固定水位/祖先路径；读档后失效，不接受调用方提供任意祖先段。当前没有公共历史查询 API。

## 15. A2 冻结契约与交付

- 独立键为 `game:archive:room:{room}:meta/pending/lease/autosaves`，全局发现队列为 `game:archive:pending_rooms` 和 `game:archive:auto_save_rooms`。仅 lease 有短 TTL；其余键不加入原运行态的清理/续期列表。
- `BindGameArchive` 是未来 start/load 操作使用的内部能力绑定，当前没有服务调用或配置入口。旧接口在检测到记忆能力时拒绝推进/重置；新内部 preflight/capture/resume 方法显式接收 timeline 与 generation。安全暂停保留待办并隔离在途世代。
- 行动与主动/超时跳过在 Lua 中校验类型、分支/世代/回合、效果和边界快照，然后同时写运行态、幂等缓存、连续 position、完整待办与队列。单人每 10 回合、多人每 5 完整轮的原边界快照随提交保留，归档 ACK 后转入独立自动存档待办；A4 才转换为完整 V3 存档。
- payload_version=1 的事实正文由 Repository 根据实际规范化效果、消息与固定响应生成；传入的非空 payload 必须完全匹配。deadline_at 与 memory 是可变交付信息，不进入正文事实哈希；原 JSON 和大整数不经过 Lua 重新编码。
- Redis 使用 double，position/revision/相关身份数字拒绝超过 `9007199254740990`；位置写入使用十进制定点格式，不允许科学计数法丢失水位。正文仍以 1 MiB 为限，边界快照也在写入前检查大小。
- Claim 同 owner token 可续租；重领、释放、重试调度及 ACK 比较 token/commit/hash/分支/位置。运行态过期不删除待办，ACK 不创建已丢失的运行态。
- ACK 连续推进 durable 一次。当前 playing 分支且来源世代/回合匹配、无控制操作时才从 Redis TIME 开始完整时限；paused/ended/控制中不启动。重复 ACK 沿用当前权威计时，旧缓存重放不携带旧 deadline。
- 提交响应丢失用新有界 context 核对完整待办、缓存和水位；已确认则返回提交成功。无法证明完整提交时返回 unknown，能访问 Redis 时设置 blocked，不把 Lua 错误当作回滚。Redis 完全不可达或全部记忆键丢失的持久化恢复/能力判定由 A3/A4 补齐，不能据 A2 宣称所有丢失可检测。
- miniredis 与真实 Redis 7.2 均验证；CI 的记忆作业增加 Redis 服务及显式 `^TestGameArchiveRedis72` race 选择器。真实 Redis 验证曾暴露 nil 效果数组编码为 null 的 Lua 遍历错误，已统一编码为数组并回归。

### 12.3 A4 实施补充

`game_memory.new_rooms_enabled` 默认为 false，仅控制新房间入口；现有能力房间继续走生命周期和恢复 worker。A5/A6 完成前不要开启该入口。旧房间不自动转换，旧存档加载到新模式才建立不完整恢复根。

V3 `memory.summary_source` 使用 `opening/runtime/legacy` 表示摘要捕获来源；摘要/近期消息仍只写原列。新模式手动存档保持 paused，原自动存档周期不变，精确 ACK 前保留原边界快照。

控制阶段仍为 prepared→redis_applied→completed。Redis 的控制 token 和 operation/hash 回执无 TTL；MySQL completed 操作在精确回执核对前继续参与恢复扫描，成功核对后 next_retry_at 设为年 9999 的终止哨兵，避免完成 MySQL 后丢失 Redis 解锁/清理。无需新增表或阶段。旧回执只能确认原操作，不得重新应用目标或清理后续分支；普通运行态丢失可从已封存目标恢复 paused，独立账本丢失则保留损坏状态。

实现和本地故障证据见 [A4 验证记录](./M3.1-A验收记录.md)。下一块 A5 接入请求 ID、状态契约、预期分支和最小恢复界面，A6 再验完整故障矩阵；多模型兼容层继续延期至 A0—A6 整体验收完毕。
