## 历史关键事件补录

新增 `go-backend/cmd/backfill-key-events` 管理命令。使用 Go 的 `configs/config.yaml` / `TRPG_DATABASE_*` 配置连接 MySQL；无需 Redis、Milvus 或模型密钥。命令仅处理指定房间的一条时间线，不提供公共接口，不自动扫描所有房间。

在 `go-backend` 目录运行，先预览：

```powershell
go run ./cmd/backfill-key-events --room 123 --timeline <时间线UUID> --batch 100 --max-batches 1
```

每批输出一个 JSON 检查点，包含 `next_position`、冻结的 `through_position`、扫描记录数、缺失事件数、实际插入数和 `done`。预览不写入；**预览的 next_position 不能作为首次写入的起点**，首次写入仍从 0 或原有已写入检查点开始。

```powershell
# 首次写入；through 使用预览的冻结水位，after 从 0 开始
go run ./cmd/backfill-key-events --room 123 --timeline <时间线UUID> --through 456 --batch 100 --max-batches 1 --apply

# 继续写入；after/through 使用上一次成功写入输出的检查点
go run ./cmd/backfill-key-events --room 123 --timeline <时间线UUID> --after 100 --through 456 --batch 100 --max-batches 1 --apply
```

- 每个事务扫描 1—100 条记录，每次命令最多 1—1000 批，默认一批；每批超时 30 秒。固定水位之后的新行动留给下一次独立运行。
- 校验连续位置、来源内容 hash 和结构化 `effects.events` / `multiplayer_effects.events`；来源缺失、篡改、无效候选或已存在的事件内容冲突，会回滚整个失败批次，不推进检查点。
- 同时间线补录与归档共用数据库行锁。已有相同事件保持原值，仅插入缺失的来源序号，并保留来源档案时间。进程中断或提交响应丢失后，可用前一个检查点重复执行。
- 子分支从自己的 `fork_position` 之后开始；祖先需分别运行。可以修补已封存的旧分支，公开读取仍按有效祖先水位过滤，旧分支未来不会出现在当前分支。
- 没有结构化事件候选的旧档案不会生成事件，旧存档有限消息也不会被伪造成完整行动历史。命令不改写档案、摘要、存档或运行水位，不新增迁移。

本机测试涵盖：实际 CLI 预览/写入/检查点续跑、单人和多人来源、并发重复补录、冻结水位、原始时间保留、不同房间与分支隔离、空 hash、payload 篡改、位置缺口、冲突/额外事件以及整批回滚。

## 摘要恢复修复

worker 在新摘要生成失败后，仍会尝试把 MySQL 中已经提交的旧摘要投影到 Redis。投影脚本允许重建缺失的摘要键，校验分支、revision、水位、控制操作与运行状态；重建使用当前运行 generation 键的剩余 TTL。已有摘要的剩余 TTL 不被延长，运行已过期或已结束时不重建缓存。Redis 错误仅记房间和错误分类，后续轮询重试。

单人/多人测试依次执行：第一周期 503 → 重新创建 worker → 摘要版本 1；新增行动 → 删除摘要缓存 → 第二周期 503 → 恢复版本 1 并保留未总结消息 → 重试生成版本 2。旧存档仍保持版本 1 和原覆盖水位。另测缓存 TTL、旧版本/水位、错误分支/revision、控制操作、结束及运行过期边界。
