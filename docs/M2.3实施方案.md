## 1. 目标

M2.3 在 M2.2 已验收的统一会话、可靠消息和断线补推链路上，交付真人群组与群聊闭环：

- 创建群组时原子创建唯一群会话和群主成员关系。
- 提供群资料、群列表、成员列表、邀请、退群、移除、角色调整和群主转让。
- 群文本消息复用 `conversations`、`conversation_members` 和 `messages`，不建立第二套消息表。
- 成员变化生成持久化系统消息，并向受影响在线用户推送群资料、成员和会话更新。
- 每次发送、拉取、已读和补推都校验当前群成员状态。
- 在群消息扇出前落实每连接 IM 业务消息速率限制，关闭 DEV-010。
- 提供 Vue 群列表、群管理和复用现有聊天面板的群聊界面。

## 3. 已确认的产品与实现决策

以下默认值已由开发者确认并冻结，M2.3-B—D 均以此为准。

1. 一个群最多 **50 名有效成员**，群主计入；单次邀请最多 20 人，事务全成或全败。
2. 邀请只允许选择当前好友，成功后立即入群，不增加邀请申请表或待确认状态。
3. 群主可修改资料、邀请、移除任意非群主成员、调整管理员和转让群主；管理员可邀请好友、移除普通成员；普通成员只能查看、聊天和主动退群。
4. 管理员不能调整角色、移除其他管理员或群主；任何操作者都不能移除群主。
5. 群主不能直接退群，也不提供解散接口；必须先原子转让群主。
6. 新成员和重新入群成员可读取完整历史；退出或被移除后立即失去群详情、历史、同步、已读和发送权限。该选择复用现有 `conversation_members.status`，不增加历史可见水位。
7. 同一用户重新入群时复用原 `group_members` 和 `conversation_members` 行，状态改回 `active`，并保留其单调 `last_read_seq`；未读数从原水位继续计算。
8. 群成员管理只改变群内权限，不自动改变好友关系；删除好友也不会自动退出共同群组。
9. 系统消息计入会话 seq 和未读数。`sender_id` 使用实际操作者，`metadata.event` 是客户端渲染的权威，`content` 只作为兼容回退文案。
10. 群资料更新使用 `groups.version` 乐观并发控制；成员变更和群主转让锁定群行并使 `version + 1`。
11. `chat_message` 与 `im_sync` 共用每连接令牌桶：每秒补充 10 个令牌、突发容量 20；发送消息消耗 1，补推消耗 5，`ping` 不消耗。超限返回 `1717 rate limited`，不关闭连接。
12. 群消息仍遵循“先提交 MySQL、后尽力推送”；发送者收到 `chat_ack`，其余有效成员收到 `chat_message`，所有有效成员收到各自视角的 `conversation_updated`。

## 4. 数据库设计

统一使用 MySQL 8.4、`BIGINT UNSIGNED`、`DATETIME(3)` 和 `utf8mb4_unicode_ci`；延续项目规则，不创建外键，由 Service 显式事务保证一致性。

### 4.1 `groups`

| 字段 | 类型与约束 | 用途 |
|---|---|---|
| `id` | `BIGINT UNSIGNED` 自增主键 | 群组 ID |
| `name` | `VARCHAR(80) NOT NULL` | 群名称，1—80 个 Unicode 字符 |
| `avatar_url` | `VARCHAR(2048) NOT NULL DEFAULT ''` | 群头像 URL |
| `owner_id` | `BIGINT UNSIGNED NOT NULL` | 当前群主用户 ID |
| `version` | `BIGINT UNSIGNED NOT NULL DEFAULT 1` | 乐观并发版本 |
| `created_at`、`updated_at` | `DATETIME(3)` | 创建与更新时间 |

索引：`(owner_id, id)` 用于按群主查询。`owner_id` 必须同时对应一条有效 `group_members.role='owner'`，由同一事务维护。

### 4.2 `group_members`

| 字段 | 类型与约束 | 用途 |
|---|---|---|
| `id` | `BIGINT UNSIGNED` 自增主键 | 成员关系 ID |
| `group_id` | `BIGINT UNSIGNED NOT NULL` | 群组 ID |
| `user_id` | `BIGINT UNSIGNED NOT NULL` | 用户 ID |
| `role` | `VARCHAR(16)`，`owner/admin/member` | 群角色 |
| `status` | `VARCHAR(16)`，`active/left` | 当前成员状态 |
| `joined_at` | `DATETIME(3) NOT NULL` | 最近一次入群时间 |
| `left_at` | 可空 `DATETIME(3)` | 最近一次退出或被移除时间 |
| `created_at`、`updated_at` | `DATETIME(3)` | 首次创建与更新时间 |

约束与索引：

- `UNIQUE(group_id, user_id)`，重新入群更新原行。
- `(user_id, status, group_id)` 支持当前用户群列表。
- `(group_id, status, role, user_id)` 支持成员列表、人数和权限查询。
- CHECK 限定角色与状态枚举。

### 4.3 与统一会话表的映射

创建群组的同一事务内必须完成：

1. 插入 `groups`。
2. 插入 `conversations(type='group', group_id=<group.id>)`；现有 `UNIQUE(group_id)` 保证一群一会话。
3. 插入群主 `group_members(role='owner', status='active')`。
4. 插入群主 `conversation_members(role='owner', status='active')`。

`group_members` 是群资料和管理权限权威；`conversation_members` 是聊天访问、角色快照和已读水位权威。邀请、退出、移除、角色调整和转让必须在同一事务中镜像更新两张成员表，任何一步失败都整体回滚。

### 4.4 成员状态迁移

```text
不存在 ──邀请──> active/member
left ────再次邀请──> active/member
active/member ──群主提升──> active/admin
active/admin ───群主降级──> active/member
active/member|admin ──退出或被移除──> left/member
active/owner ──转让──> active/member
目标 active/member|admin ──接任──> active/owner
```

- 再次邀请时更新 `joined_at`、清空 `left_at`，但不回退 `last_read_seq`。
- 离群后统一把两张成员表的角色归一为 `member`，避免重新入群继承管理员权限。
- 群主转让必须锁定 `groups`、原群主和新群主的两套成员行，在一个事务中交换角色、更新 `owner_id` 和递增版本。

## 5. REST 契约

所有接口位于 `/api/v1`，使用 JWT 和统一响应信封。群不存在、已离群和从未入群统一返回 `1801 group not found`，避免泄露私有群信息。

| 方法 | 路径 | 说明 |
|---|---|---|
| `POST` | `/groups` | 创建群组；`{name, avatar_url?}` |
| `GET` | `/groups` | 当前有效群组稳定游标列表 |
| `GET` | `/groups/{groupId}` | 群详情、当前用户角色和会话 ID |
| `PATCH` | `/groups/{groupId}` | 群主更新名称/头像；携带 `expected_version` |
| `POST` | `/groups/{groupId}/members` | 群主或管理员批量邀请好友；`{user_ids, expected_version}` |
| `GET` | `/groups/{groupId}/members` | 按成员关系 ID 倒序稳定分页 |
| `PATCH` | `/groups/{groupId}/members/{userId}` | 群主调整 `admin/member`；携带 `expected_version` |
| `DELETE` | `/groups/{groupId}/members/{userId}` | 自己退群，或有权限者移除成员；查询参数 `expected_version` |
| `POST` | `/groups/{groupId}/transfer` | 群主转让；`{new_owner_user_id, expected_version}` |

关键响应结构：

```json
{
  "id": 9,
  "name": "周五夜调查局",
  "avatar_url": "",
  "owner_id": 7,
  "conversation_id": 41,
  "current_user_role": "owner",
  "member_count": 3,
  "version": 4,
  "created_at": "2026-09-15T12:00:00Z",
  "updated_at": "2026-09-15T12:05:00Z"
}
```

### 5.1 幂等与并发

- 创建群组不是自然幂等操作，前端提交期间必须禁用重复点击；本里程碑不额外引入 REST 幂等键。
- 邀请已在群内的用户、移除已离群用户、把成员改成当前角色均作为成功的无状态变化返回，不生成重复系统消息，也不递增版本。
- 真实状态变化必须满足 `expected_version == groups.version`；不满足返回 HTTP 409 / `1806 group version conflict`。
- 批量邀请先校验全部用户存在、好友关系、容量和权限，再写入；不允许部分成功。

### 5.2 错误码

| 代码 | HTTP | 场景 | 安全文案 |
|---:|---:|---|---|
| `1800` | 400 | 请求字段、游标或成员集合非法 | `invalid group request` |
| `1801` | 404 | 群不存在或当前用户不可见 | `group not found` |
| `1802` | 403 | 当前角色无操作权限 | `group permission denied` |
| `1803` | 409 | 邀请目标不是当前好友 | `group friendship required` |
| `1804` | 409 | 群成员已满 | `group member limit reached` |
| `1805` | 409 | 群主尝试退出或非法转让 | `group owner conflict` |
| `1806` | 409 | `expected_version` 已过期 | `group version conflict` |
| `1807` | 500 | 群服务或事务失败 | `group unavailable` |

## 6. 会话与消息契约扩展

### 6.1 判别联合摘要

当前 `ConversationSummary.peer` 必填且仓储查询只返回 `direct`。M2.3-B 必须将摘要升级为由 `type` 判别的联合，不能为群聊伪造 peer：

```ts
type ConversationSummary =
  | (ConversationBase & {
      type: 'direct'
      peer: PublicUser
      group: null
    })
  | (ConversationBase & {
      type: 'group'
      peer: null
      group: {
        id: number
        name: string
        avatar_url: string
        current_user_role: 'owner' | 'admin' | 'member'
        member_count: number
        version: number
      }
    })
```

`can_send` 对私聊表示好友关系仍为 accepted；对群聊表示当前 `conversation_members.status='active'`。群会话列表不逐行查询成员数或发送者，仓储必须用批量查询或聚合避免 N+1。

### 6.2 群文本消息

客户端 `chat_message` 结构不变。`SendMessage` 在锁定会话后按类型分支：

- `direct`：继续锁定 accepted 好友关系并校验有效会话成员。
- `group`：锁定并校验发送者有效 `group_members` 与 `conversation_members`；不要求与其他成员互为好友。

seq 分配、幂等键、正文限制、发送者已读推进和错误映射继续复用 M2.2。

### 6.3 系统消息

系统消息与群成员/资料变更在同一事务内写入，使用服务端 UUID，只有真实状态变化才分配 seq。建议事件：

- `group_created`
- `group_name_changed`
- `group_avatar_changed`
- `member_joined`
- `member_left`
- `member_removed`
- `member_role_changed`
- `owner_transferred`

```json
{
  "message_type": "system",
  "content": "Alice 邀请 Bob 加入群组",
  "metadata": {
    "event": "member_joined",
    "actor_user_id": 7,
    "target_user_id": 8,
    "group_id": 9,
    "group_version": 4
  }
}
```

客户端只允许发送 `text`，不能提交 `system`。Vue 优先按 `metadata.event` 和当前用户资料渲染，`content` 仅供旧客户端回退。

## 7. WebSocket 实时事件与扇出

### 7.1 群文本消息

事务提交后：

1. 当前连接收到带相同 `request_id` 的 `chat_ack`。
2. 除发送者外的所有有效群成员收到 `chat_message`。
3. 全部有效群成员收到各自视角的 `conversation_updated`。
4. 任一推送失败只记录不含消息正文的结构化日志，不回滚消息；REST/`im_sync` 最终补齐。

重复发送只返回 `chat_ack(duplicate=true)`，不重新广播。

### 7.2 群变化事件

沿用 M2.0-A 预留名称：

```json
{
  "type": "group_updated",
  "timestamp": 1789464000000,
  "data": {"group": {"id": 9, "name": "周五夜调查局", "version": 4}}
}
```

```json
{
  "type": "group_member_changed",
  "timestamp": 1789464000000,
  "data": {
    "group_id": 9,
    "event": "member_removed",
    "actor_user_id": 7,
    "target_user_id": 8,
    "version": 5
  }
}
```

- 资料、角色和成员变化推送给变更后的全部有效成员。
- 退出或被移除的目标用户也单独收到 `group_member_changed`，前端据此移除群与会话；该事件不是历史授权，收到后仍不能拉取群数据。
- 同一次变更生成的系统消息通过 `chat_message` 推给变更后的有效成员，并通过 `conversation_updated` 刷新摘要。
- MySQL 始终是权威；客户端收到事件后按 ID 合并，版本倒退的事件直接忽略。

### 7.3 每连接速率限制

令牌桶放在 `imws.Client` 入站分发边界，作用域为当前物理连接：

- 严格信封解析成功后、调用业务 Handler 前扣令牌。
- `chat_message` 成本 1，`im_sync` 成本 5，`ping` 和未知类型不消耗。
- 令牌不足时返回带原 `request_id` 的 `1717 rate limited`，不调用 Service、不写库、不关闭连接。
- 连接接管后新连接获得新桶；不把令牌状态放 Redis，也不承诺跨实例全局限流。
- 使用单调时钟并在 Client 单线程读取路径内更新；补充突发、稳定速率、不同成本和接管重置测试。

## 8. 权限与事务边界

| 操作 | owner | admin | member |
|---|:---:|:---:|:---:|
| 查看群、成员、历史 | 是 | 是 | 是 |
| 发送群消息、推进已读、补推 | 是 | 是 | 是 |
| 修改群名称或头像 | 是 | 否 | 否 |
| 邀请当前好友 | 是 | 是 | 否 |
| 移除普通成员 | 是 | 是 | 否 |
| 移除管理员 | 是 | 否 | 否 |
| 调整管理员 | 是 | 否 | 否 |
| 转让群主 | 是 | 否 | 否 |
| 主动退群 | 转让后 | 是 | 是 |

成员变更事务统一顺序：

1. `SELECT groups ... FOR UPDATE`。
2. 校验 `expected_version`、操作者有效成员关系和角色。
3. 按升序锁定目标用户、好友关系及两套成员行，避免批量邀请死锁。
4. 更新 `groups`、`group_members`、`conversation_members`。
5. 锁定群会话、分配系统消息 seq、更新会话最后消息和操作者已读水位。
6. 提交后才执行在线事件扇出。

所有非成员查询统一表现为不存在；发送时在事务内重新校验，不依赖连接时或页面加载时的旧权限。

## 10. 验收标准

- 并发创建、邀请、移除、角色调整和转让不产生孤儿、双群主或两表角色漂移。
- 50 人容量在并发邀请下不能突破；批量邀请不部分成功。
- 非好友不能被邀请；成为群友后删除好友不影响群聊。
- 普通成员、管理员和群主权限严格符合矩阵；越权响应不泄露群信息。
- 新成员可读取完整历史；退出或被移除后所有 REST、发送和 `im_sync` 均立即失败，重新入群后恢复。
- 群消息并发发送时 seq 连续唯一；同一请求重试不新增消息或重复扇出。
- 系统消息与成员状态同事务提交，状态未改变时不产生重复系统消息。
- 在线成员收到消息与群事件；离线成员重连后按 MySQL seq 完整补齐。
- 速率超限不触发 DB/Service，恢复速率后同连接可继续使用。
- direct 私聊所有既有测试继续通过，前端私聊体验无回归。
- OpenAPI 路由契约、Go test/vet/build、Vue test/build、Python 回归、迁移测试、Compose 解析和 targeted race 全部通过。
- 至少三个真实账号完成创建群、邀请、双向群聊、管理员权限、退群/移除、重加、群主转让、离线恢复和连接接管验收。

## 11. 主要风险与控制

| 风险 | 控制 |
|---|---|
| `group_members` 与 `conversation_members` 双写漂移 | 所有变更同事务；集成测试与一致性查询覆盖 |
| 群广播形成 N+1 查询或长时间阻塞 ack | 批量加载收件人/摘要；提交后独立超时尽力推送；后续可异步化 |
| 成员变更与发送竞态导致离群后仍写入 | 两条路径锁群/会话并在事务内校验有效成员 |
| 版本事件乱序覆盖新状态 | MySQL 版本权威；客户端只接受更高版本 |
| 高频 `im_sync` 放大数据库压力 | 加权令牌桶，sync 成本高于发送；单次仍限制 100 条 |
| 大群会话摘要聚合变慢 | 50 人上限、必要索引、批量聚合，禁止逐会话逐成员查询 |
| 无外键产生孤儿记录 | 显式事务、删除/失活路径测试和一致性检查 |
