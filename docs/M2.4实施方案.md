# TRPGGame M2.4 多人房间与等待大厅实施方案

> **状态**：M2.4-A 产品决策已确认；M2.4-B 已提交 `6a2ed79` 并通过 CI 七个作业；M2.4-C/D 未开始
>
> **起草日期**：2026-09-18
>
> **前置基线**：M2.3 验收修复 `5b3f130`、CI #44 和三账号浏览器验收通过

## 1. 目标与边界

M2.4 复用现有 `game_rooms`、`room_players` 和 `/ws?room_id=` 游戏通道，交付可创建、凭码加入、选角、准备、离开与开局的多人等待大厅。房间状态以 MySQL 为权威，实时事件只加速界面更新；重连后可从 REST 恢复完整大厅快照。

本里程碑不实现多人 AI 推理、行动抢占、回合计时/跳过、V2 运行态/存档或跨实例广播；这些属于 M2.5。M2.4 的开局只完成房间/成员状态的事务转换与事件通知，尚不代表可进入完整多人游戏。单人 `/api/v1/games/solo/start`、V1 存档和现有游戏通道语义必须保持不变。

## 2. 已有基线与兼容约束

- `005_create_game_rooms.sql` 已定义 `waiting → playing → paused ↔ playing → ended`、`max_players`、`turn_order`、`is_solo`；`006_create_room_players.sql` 已定义每房间每用户唯一、角色、顺序与准备状态。已执行迁移不能原地修改。
- 现有 `GameService`、`GameRepo` 和 `/api/v1/games/*` 主要按房主+单人运行态实现；多人大厅使用独立 `RoomService/RoomHandler`，不要把多人分支塞入单人服务的现有事务。
- 当前 `roomAuthorizer` 只查询房主；M2.4 改为：单人房间仍限房主，多人房间允许有效成员订阅，退房/被踢后新握手立即拒绝，并主动断开已建立的旧连接。
- 游戏 Hub 已支持同用户同房间新连接接管，不在 M2.4 重新实现；IM 通道独立，不因进入大厅而断开。
- Phase 2 新迁移不设外键，所有关联与状态转换由事务保证。

## 3. 已确认的产品决策

开发者于 2026-09-18 在下表确认这些决定，M2.4-B—D 均以此为准：

| 议题 | 建议 | 需确认的取舍 | 决策回复 |
|---|---|---|---|
| 容量与开局人数 | 房主在 4—6 人之间选容量，含房主；至少 2 人且所有在场成员已选不同角色并准备才可开局 | “4—6 人”是容量范围，还是开局人数下限也必须为 4？ | 房主在 4—6 人之间选容量，含房主；至少 2 人且所有在场成员已选不同角色并准备才可开局 |
| 剧本角色不足 | 建房时要求可选预设角色数不少于设定容量 | 是否允许一角多人、创建自定义角色或降低容量？首版建议均不做。 | 都不做 |
| 房主离开等待大厅 | 仅允许先转让给其他在场成员；房主不能直接调用退出 | 是否改为自动转给最早加入者？首版建议显式转让。 | 房主需要主动转让他人才可以退出房间 |
| 开局后成员离开/踢出 | M2.4 冻结成员名单与 `turn_order`；开局后的退出、踢人及断线规则延至 M2.5 | 是否要求 M2.4 即可在游戏中主动离开？ | 按照建议左 |

其他建议默认：房间码为服务端生成的不可猜测短码，唯一约束由数据库保证；只用于加入，不替代 JWT 与成员授权。房主可以在 `waiting` 时踢出其他成员；准备状态在更换角色、重新加入和房主转让后按需清零。所有成员可读取大厅；只有房主可开局、踢人和转让。

## 4. 数据与事务设计

### 4.1 迁移 016—017

`016_extend_game_rooms.sql`：新增 `room_code`（多人非空、唯一）、`version`（乐观并发）、`turn_timeout_seconds`（为 M2.5 预留，默认 120）；仅新多人房间生成房间码，旧单人行保持兼容。真实约束与索引以 MySQL 8.4 空库/升级测试验证。

`017_extend_room_players.sql`：新增 `status`（`active`/`left`/`removed`）与 `left_at`，保留 `(room_id,user_id)` 唯一并通过更新旧行实现重新加入；增加按房间与状态列成员的索引。只有有效成员占容量和角色；同房间有效角色唯一需由数据库约束或锁定房间后的事务校验保证，不允许仅靠前端过滤。

所有大厅变更按 `SELECT game_rooms ... FOR UPDATE` → 校验版本/房间状态/操作者身份 → 锁定相关成员与角色 → 更新房间及成员 → 递增版本 → 提交后广播的顺序执行。非成员查询返回统一的“不存在或无权访问”，不泄露房间详情。容量、重复加入、并发选角、重复开局和转让必须有 MySQL 8.4 并发测试。

### 4.2 状态与幂等

`waiting` 允许加入、选角、准备、离开、踢人和转让；开局事务仅从 `waiting` 转为 `playing`，冻结成员快照与 `turn_order`。重复请求返回当前权威快照或稳定冲突码，不重复修改版本/广播。所有写请求携带 `expected_version`；版本冲突返回当前版本，客户端刷新大厅后重试。角色更换或成员变更导致相关准备状态失效，避免旧准备状态绕过开局校验。

## 5. REST 与游戏 WebSocket 契约

| 方法 | 路径 | 主要用途 |
|---|---|---|
| `POST` | `/api/v1/rooms` | 从本人已就绪剧本创建多人房间，返回房间码与快照 |
| `GET` | `/api/v1/rooms` | 列出本人有效参与的房间 |
| `GET` | `/api/v1/rooms/:roomId` | 有效成员获取大厅快照及候选角色 |
| `POST` | `/api/v1/rooms/join` | 用房间码加入或幂等返回已有成员关系 |
| `POST` | `/api/v1/rooms/:roomId/character` | 选择/更换本人的未占用剧本角色 |
| `POST` | `/api/v1/rooms/:roomId/ready` | 设置本人准备状态 |
| `POST` | `/api/v1/rooms/:roomId/leave` | 本人退出等待大厅 |
| `POST` | `/api/v1/rooms/:roomId/members/:userId/remove` | 房主踢出等待大厅成员 |
| `POST` | `/api/v1/rooms/:roomId/transfer` | 等待大厅房主转让 |
| `POST` | `/api/v1/rooms/:roomId/start` | 房主在前置条件满足时事务开局 |

响应统一包含 `id`、`status`、`version`、`owner_id`、`max_players`、成员及准备/角色状态；房间码只在有权页面展示。错误码使用 Phase 2 预留的 `1900—1999` 区间并进入 OpenAPI 与路由契约测试。

游戏通道沿用 `/ws?token=&room_id=`，M2.4 追加 `room_snapshot`、`room_member_joined`、`room_member_left`、`room_ready_changed`、`room_character_selected` 和 `game_started`。事件至少带 `room_id`、`version` 与变更后的权威摘要；断线重连先读 REST 快照，再只接受更高版本事件，避免乱序覆盖。事务失败不广播。离房/被踢者只能收到失权通知，不能继续订阅后续大厅更新。

## 6. Vue 边界

新增建房/凭码加入入口与 `/lobby/:roomId` 等待大厅；展示房间码、剧本、成员、角色占用、准备状态及开局条件。房主显示踢人、转让、开局操作；普通成员只能操作自己的角色/准备/离开。所有操作按 `version` 合并，冲突时刷新快照；断线显示连接状态并从 REST 恢复。M2.4 结束页不进入 M2.5 尚未实现的多人行动界面。

## 7. 分块与验收门

- **M2.4-A 契约评审**：确认第 3 节决策，冻结迁移字段、状态机、REST/WS 与错误码；此块不改功能代码。
- **M2.4-B 持久化与 REST**：016—017 迁移、Repo/Service/Handler/OpenAPI、MySQL 8.4 并发与单人回归；完成后先评审和提交。
- **M2.4-C 实时大厅**：成员握手授权、失权断连、版本事件、接管/断线恢复、Hub 并发回归；完成后先评审和提交。
- **M2.4-D Vue 与验收**：建房/加入/等待大厅、自动化、CI、至少三账号真实浏览器验收；完成后再进入 M2.5。

M2.4 不等同于 Phase 2 完成。Phase 1 的真实部署验收、M2.0/M2.1 的独立真实环境验收与 M2.5 多人回合仍分别保留。
