## 1. 目标

M2.1 在 M2.0 已完成的用户认证、公共 WebSocket 握手和独立 IM Hub 之上，交付好友关系与在线状态最小闭环：

- 按用户 ID、用户名或昵称前缀搜索用户。
- 发送、查看、接受和拒绝好友申请。
- 查看及删除好友。
- 通过 Redis 租约维护 IM 在线/离线状态。
- 通过 `/ws/im` 向已接受好友推送 presence 与好友关系变化。
- 提供 Vue 好友列表、申请面板和全局 IM 连接。

完成后，M2.1 的好友与在线状态代码应可独立验收，但不能将其写成 Phase 2 完整验收通过。

## 3. 已确认决策

1. 好友双方只保留一条规范化关系记录。
2. 相同方向的重复申请幂等返回当前结果。
3. 收到 pending 的一方反向发送申请时，直接转为 accepted。
4. 接受、拒绝和删除按当前关系及操作者权限幂等处理。
5. M2.1 只实际产生 `online`、`offline`；`gaming` 保留到 M2.4。
6. 好友申请和关系变化使用 `friendship_updated` 实时事件。
7. REST 列表使用稳定游标；前端汇总已加载数据后按在线状态排序。
8. Redis presence 使用连接 ID 租约和 Lua compare-and-refresh/delete，旧连接不能覆盖新连接。
9. MySQL 是好友关系权威，Redis 与 WebSocket 推送失败不能回滚已经提交的关系事务。
10. 单实例行为在 M2.1 闭环；跨实例广播与全局接管不提前实现。

## 4. 数据库设计

### 4.1 迁移

- 不修改已经执行的 001—009 迁移。

### 4.2 `friendships`

| 字段 | 类型与语义 |
|---|---|
| `id` | `BIGINT UNSIGNED` 自增主键 |
| `user_low_id` | 双方较小用户 ID |
| `user_high_id` | 双方较大用户 ID |
| `requested_by` | 当前或最近一轮申请人，必须是双方之一 |
| `status` | `pending`、`accepted`、`rejected`、`removed` |
| `created_at` | 关系行首次创建时间 |
| `updated_at` | 最近一次有效状态变化时间 |
| `responded_at` | 当前一轮接受或拒绝时间；重新申请时清空 |
| `removed_at` | 当前一轮删除时间；重新申请时清空 |

约束与索引：

- `CHECK (user_low_id < user_high_id)`。
- `CHECK (requested_by IN (user_low_id, user_high_id))`。
- 状态值 CHECK。
- `UNIQUE KEY (user_low_id, user_high_id)`。
- `KEY (user_low_id, status, id)`。
- `KEY (user_high_id, status, id)`。
- `users` 增加以 `nickname` 开头、覆盖 ID 与软删除判断的查询索引。

关系行在删除和重新申请时复用，保持稳定 ID，但不声称保存完整审计历史。如后续需要完整历史，另建事件表，不扩张 M2.1。

## 5. 好友状态机

### 5.1 发送申请

| 当前状态 | 操作 | 结果 |
|---|---|---|
| 不存在 | 任一方申请 | 创建 `pending`，`requested_by=操作者` |
| `pending`，操作者为原申请人 | 重复申请 | 幂等返回现有 `pending` |
| `pending`，操作者为接收人 | 反向申请 | 原子转换为 `accepted` |
| `accepted` | 任一方申请 | 幂等返回现有 `accepted` |
| `rejected` 或 `removed` | 任一方重新申请 | 转为 `pending`，重置申请人与本轮时间字段 |

禁止向自己申请；目标用户必须存在且未软删除。

### 5.2 接受与拒绝

- 只有当前 `pending` 的接收人可以接受或拒绝。
- 接收人重复接受已经 accepted 的同一关系时返回当前结果。
- 接收人重复拒绝已经 rejected 的同一关系时返回当前结果。
- 申请人主动调用接受或拒绝返回禁止操作。
- accepted 与 rejected 的竞争由行锁串行化；后到操作按已经提交的状态返回幂等结果或状态冲突。

### 5.3 删除

- 任一方可以删除 accepted 好友。
- 删除转换为 `removed`，写入 `removed_at`，不物理删除关系行。
- 同一参与方重复删除 removed 关系视为成功。
- 从未建立或当前不是 accepted/removed 的关系返回“好友关系不存在”。

### 5.4 并发策略

- Service 先规范化双方 ID。
- 使用双方唯一键消除正反两条记录。
- 事务内对已有行执行 `SELECT ... FOR UPDATE`。
- 行不存在时用幂等插入建立唯一行；唯一键竞争后重新读取并加锁。
- 状态判断和更新在同一事务内完成。
- 提交成功后才发布 `friendship_updated`，发布失败只记录日志并由 REST/后续刷新恢复。

必须覆盖同向并发申请、反向并发申请、重复接受、接受/拒绝竞争、接受/删除竞争和删除后重加。

## 6. REST 契约

所有接口位于 `/api/v1`、要求 Bearer Access Token，并继续使用统一响应信封。

### 6.1 用户搜索

`GET /api/v1/users/search?keyword=<value>`

- `keyword` 去除首尾空白后必填，最多 50 个 Unicode 字符。
- 正整数关键字精确匹配用户 ID。
- 用户名精确匹配，沿用当前数据库排序规则。
- 非纯数字关键字达到 2 个字符后执行昵称前缀搜索。
- 排除当前用户及软删除用户；结果去重，最多 20 项。
- 排序顺序为精确 ID、精确用户名、昵称前缀，再按用户 ID。
- 不返回邮箱、密码字段或非好友 presence。

每项返回：

```json
{
  "user": {
    "id": 8,
    "username": "player08",
    "nickname": "调查员",
    "avatar_url": ""
  },
  "friendship": {
    "id": 31,
    "status": "pending",
    "direction": "outgoing"
  }
}
```

不存在关系时 `friendship` 为 `null`；`direction` 只在 pending 时为 `incoming` 或 `outgoing`。

### 6.2 发送申请

`POST /api/v1/friend-requests`

```json
{"target_user_id": 8}
```

首次创建、重复申请、反向自动接受和已经为好友都返回 HTTP 200 及当前权威关系，便于客户端安全重试。

### 6.3 申请列表

`GET /api/v1/friend-requests?direction=incoming|outgoing&status=pending|rejected&cursor=&limit=`

- `direction` 默认 `incoming`。
- `status` 默认 `pending`。
- `limit` 默认 20，最大 100。
- 游标基于不可变关系 ID，按 ID 倒序分页。
- accepted 关系只出现在好友列表；removed 不作为申请历史公开。

返回 `items` 和可空 `next_cursor`。

### 6.4 接受与拒绝

- `POST /api/v1/friend-requests/{requestId}/accept`
- `POST /api/v1/friend-requests/{requestId}/reject`

成功返回当前权威关系和对端用户摘要。

### 6.5 好友列表

`GET /api/v1/friends?cursor=&limit=`

- 只返回 accepted 关系。
- `limit` 默认 50，最大 100。
- 后端按关系 ID 倒序稳定分页，不按动态 presence 做数据库分页。
- 每项包含对端用户摘要、关系 ID、accepted 时间语义的 `updated_at` 和 presence。
- 前端汇总已加载项目后按 `gaming`、`online`、`unknown`、`offline` 排序，再按显示名和用户 ID 排序；M2.1 不产生 gaming。

### 6.6 删除好友

`DELETE /api/v1/friends/{friendUserId}`

成功返回 `{"code":0,"message":"ok"}`。关系变化通过 `friendship_updated` 尽力推送给双方。

## 7. 错误码

| 业务码 | HTTP | 含义 |
|---|---:|---|
| `1600` | 400 | 好友模块请求参数无效 |
| `1601` | 404 | 目标用户不存在 |
| `1602` | 400 | 不能向自己发送好友申请 |
| `1603` | 404 | 好友申请不存在 |
| `1604` | 403 | 无权处理该好友申请 |
| `1605` | 409 | 好友关系状态冲突 |
| `1606` | 404 | 好友关系不存在 |
| `1607` | 400 | 分页参数或游标无效 |
| `1699` | 500 | 好友模块内部错误 |

Handler 只负责参数、HTTP 状态和安全文案映射；目标存在性、参与者权限、状态机和幂等逻辑全部放在 Service。

## 8. Presence 设计

### 8.1 M2.1 状态语义

| 状态 | M2.1 语义 |
|---|---|
| `online` | 用户当前拥有有效 IM WebSocket 租约 |
| `offline` | Redis 中不存在有效 IM 租约 |
| `unknown` | 查询 Redis 失败，不能安全断言离线 |
| `gaming` | 公共契约保留；M2.4 根据权威房间状态接入，M2.1 不产生 |

presence 只向 accepted 好友公开。搜索结果和 pending 申请不泄露在线状态。

### 8.2 Redis 租约

- Key：`presence:user:{user_id}:im`。
- Value：当前 IM `connection_id`。
- TTL：默认 90 秒。
- 新连接注册成功后 claim 租约。
- 收到当前连接的协议 Pong 后 compare-and-refresh TTL。
- 当前连接注销、慢连接清理或 Hub 停止时 compare-and-delete。
- missing key 表示 offline；Redis 命令错误表示 unknown。

claim、refresh、release 均使用 Lua。refresh/release 只有在 Value 等于调用方 connection ID 时才生效，确保旧连接的延迟事件不能续租或删除新连接。

### 8.3 Hub 生命周期接入

M2.0 文档预留了 `PresenceObserver`，但当前生产代码尚未实现。M2.1-C 补充：

```go
type PresenceObserver interface {
    OnConnected(userID uint, connectionID string)
    OnRefreshed(userID uint, connectionID string)
    OnDisconnected(userID uint, connectionID string)
}
```

- Observer 在 `Hub.Run` 前注入。
- `connected` 仍必须是新客户端收到的第一条消息；成功入队后再通知 Observer。
- 替换连接只 claim 新 connection ID，不为旧连接产生 offline 抖动。
- unregister 仅在客户端仍为当前连接时发出 disconnected。
- send buffer 满导致删除当前连接时必须发出 disconnected。
- `closeAllClients` 必须为每个当前连接发出 disconnected。
- Pong 续租前必须验证 Client 仍是 Hub 当前连接。

Observer 不直接在 Hub 事件循环中访问 Redis。Presence Coordinator 使用有序缓冲事件队列处理 Redis 与好友查询，保证同一进程内事件顺序；队列关闭时应排空，服务退出顺序为 IM Hub → Presence Coordinator → Redis Client。

### 8.4 presence 广播

- claim 从离线变在线时，向当前 accepted 好友广播 online。
- 替换连接时状态未变化，不重复广播 online。
- 当前租约成功释放时广播 offline。
- 续租不广播。
- 广播前重新查询 MySQL accepted 好友，关系数据库是权限权威。
- 广播失败不回滚 Redis 租约；好友列表查询可恢复当前状态。

## 9. IM WebSocket 契约

M2.1 不新增客户端业务消息类型，继续只接受 `ping`。

### 9.1 `presence`

```json
{
  "type": "presence",
  "timestamp": 1789056000000,
  "data": {
    "user_id": 8,
    "status": "online"
  }
}
```

M2.1 实时推送只使用 online/offline；unknown 只用于 REST 降级结果。

### 9.2 `friendship_updated`

```json
{
  "type": "friendship_updated",
  "timestamp": 1789056000000,
  "data": {
    "friendship_id": 31,
    "status": "accepted",
    "requested_by": 7,
    "peer": {
      "id": 8,
      "username": "player08",
      "nickname": "调查员",
      "avatar_url": ""
    },
    "updated_at": "2026-09-10T10:00:00.000Z"
  }
}
```

- 事务提交后分别构造双方视角的 peer 并尽力投递。
- pending、accepted、rejected、removed 均可推送。
- 客户端收到后重新获取受影响列表，事件不是持久化同步替代品。
- 离线用户不会补推该事件；MySQL REST 查询始终返回权威结果。

## 14. 风险与控制

| 风险 | 控制 |
|---|---|
| 正反申请生成两条关系 | 规范化双方 ID + 唯一键 + 事务重读 |
| 旧连接把新连接标离线 | Redis Value 保存 connection ID，refresh/release 使用 Lua CAS |
| Redis 阻塞 IM Hub | Observer 只入有序队列，Coordinator 执行外部 I/O |
| 动态在线排序导致游标漂移 | REST 按不可变关系 ID 分页，前端对已加载集合排序 |
| 搜索泄露隐私 | 不支持邮箱搜索，不返回邮箱，只向 accepted 好友暴露 presence |
| 实时推送与 MySQL 不一致 | MySQL 先提交且始终权威，事件只用于刷新提示 |
| SQL Mock 掩盖 MySQL 锁语义 | 增加 MySQL 8.4 CI 集成测试 |
| 多页面连接互相接管 | 4001 为终止重连条件，旧页面明确提示 |
| 过早引入 gaming 导致语义错误 | M2.1 仅 IM online/offline，M2.4 按房间权威状态接入 |

## 15. 完成定义

M2.1-A 完成必须满足：

1. 反向申请、幂等和删除重加语义明确。
2. REST 路径、请求、响应、分页和错误码明确。
3. Redis Key、TTL、连接 ID CAS 和 unknown 降级明确。
4. Hub Observer 的接入与关闭顺序明确。
5. presence 与 friendship_updated 契约明确。
6. gaming 延后到 M2.4 的边界明确。
7. Vue 全局 IM 生命周期和 4001 行为明确。
8. B/C/D 实施边界及各自验收标准明确。
9. 相关状态文档同步，且没有新增生产代码或数据库迁移。

M2.1-A 完成后停止，等待开发者确认是否进入 M2.1-B。
