# M3.1-B 关键事件与摘要实施方案

> 状态：B1 关键事件归档、读取和最小界面已编码并通过本地门禁；B2 摘要闭环与 B3 上下文预算尚未完成。整个 M3.1-B 未验收。

## B1 已实现边界

- `021_create_key_events.sql` 增加只追加的关键事件表。事件绑定房间、时间线、归档位置、来源 `commit_id` 和来源内序号；同来源序号唯一，不建立外键。旧 001—020 迁移不改写。
- 只解析已校验行动结果中的 `effects.events` / `multiplayer_effects.events`。正式行动档案与事件在同一 MySQL 事务写入；失败则档案与水位一同回滚，重试和重复领取不会重复事件。普通叙事里的关键词不会产生事件。
- `GET /api/v1/games/{roomId}/key-events` 仅允许单人房主或多人有效成员。调用方传入当前 `timeline_id`；按位置和来源内序号分页，读档后旧时间线请求返回冲突。列表按祖先可见水位读取，事件附带来源行动和正式叙事，界面可展开核查。
- 新模式仍按 A 的开关默认关闭。迁移增加表结构，但不改变旧房间行动路径。迁移前已归档的事件候选尚未补录，属于 B 的后续兼容工作。

## B2 摘要闭环待实现

摘要以 MySQL 中的已归档行动为唯一事实输入，不能从临时流片段或未确认 Redis 结果生成。计划为每条时间线保存摘要正文和 `summary_through_position`，并在新正式叙事累计五次时安排持久任务；跳过不计数。异步任务调用 Python 摘要服务，回写时校验房间、当前时间线、来源水位及旧摘要版本；失败保留旧摘要并重试。读档新分支从存档摘要和其明确水位建立基线，旧任务不能覆盖新分支。运行态摘要的发布须由 Go 在水位校验后完成，避免 Python 直接改写权威状态。

## B3 上下文预算待实现

近期窗口仍为最多 10 条消息；摘要水位落后窗口时，用有预算的已归档消息补齐并标明降级。当前状态与系统规则优先，关键事件去重且有固定预算；剧本 RAG 和未来历史召回先被裁剪。为这条链路补充长文本和故障测试后，才标记 M3.1-B 验收。
