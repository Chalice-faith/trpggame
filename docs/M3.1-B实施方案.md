# M3.1-B 关键事件与摘要实施方案

> 2026-10-09：B1—B3 代码已实现，完成本机普通回归与真实 MySQL/Redis 集成验证；真实 DeepSeek 和目标部署验收仍待执行。新房间开关默认关闭，整个 M3.1-B 尚未完成生产验收。

## B1 已实现边界

- `021_create_key_events.sql` 增加只追加的关键事件表。事件绑定房间、时间线、归档位置、来源 `commit_id` 和来源内序号；同来源序号唯一，不建立外键。旧 001—020 迁移不改写。
- 只解析已校验行动结果中的 `effects.events` / `multiplayer_effects.events`。正式行动档案与事件在同一 MySQL 事务写入；失败则档案与水位一同回滚，重试和重复领取不会重复事件。普通叙事里的关键词不会产生事件。
- `GET /api/v1/games/{roomId}/key-events` 仅允许单人房主或多人有效成员。调用方传入当前 `timeline_id`；按位置和来源内序号分页，读档后旧时间线请求返回冲突。列表按祖先可见水位读取，事件附带来源行动和正式叙事，界面可展开核查。
- 新模式仍按 A 的开关默认关闭。迁移增加表结构，但不改变旧房间行动路径。迁移前已归档的事件候选尚未补录，属于 B 的后续兼容工作。

## B2 摘要闭环

- 追加 022—024 迁移，不改写 001—021。摘要包含房间、时间线、版本、覆盖位置和来源 hash；持久任务保存事实范围、旧摘要、消息、租约、重试次数和错误分类。
- 默认五次正式行动触发；开场可作为输入，跳过不计数。任务按时间线和旧版本唯一，每次最多 100 条来源记录；达到上限时允许提前压缩，完全无叙事的窗口直接沿用摘要并推进水位，避免长跳过积压永久堵塞。
- Python 鉴权内部接口 `/api/v1/ai/memory/summary` 仅生成 200—500 字候选。失败保留旧摘要并退避重试，重启可重新领取过期租约。
- Go 回写锁定房间与状态，复核租约、当前时间线、revision、消息、来源 hash 和旧版本。读档后的旧响应不能覆盖新分支。
- 存档冻结摘要正文、来源时间线、版本与覆盖水位，并校验内容 hash；旧分支后来生成的摘要不会反向改变已保存基线。旧 V1/V2/V3 存档新增字段可空，兼容升级路径。
- MySQL 是权威来源，Redis 是投影。Lua 校验分支、revision、归档/控制状态、水位，版本及水位不可倒退，保留 TTL。投影失败由后续轮询重建。

## B3 上下文预算

- Go 提供分支可见摘要、最近十条正式记录与未被摘要覆盖记录的并集，每条记录可含多条对话，避免重复。旧快照导入的有限消息作为已知基线，保持 `history_complete=false`。
- 最多读取 100 条记录，缺口超限取最近 100 条并设置 `degraded`。关键事件最多 20 条并去重，Python 再应用总长度预算。
- 默认输入预算 24000、窗口 32768、输出预留 4096、安全余量 1024。使用 UTF-8 字节数作保守上界，**不是供应商精确 token 计数**。行动推理另为工具定义、工具结果和封装预留空间；最终 LLM 请求统一检查消息及工具定义。
- 完整规则、当前行动、角色资料和权威状态优先，无法容纳则拒绝调用。可选内容按 RAG 尾部、最旧对话、事件、摘要的顺序裁剪；裁剪不删除原始档案，摘要和事件另有独立上限。
- `context_budget` 日志记录分项估算、预留、裁剪数量和降级标记，不记录正文。工具结果过大则拒绝继续生成，避免截断权威结果。
