## 1. 目标

M2.0-A 负责冻结实时通信的安全配置、IM 消息信封和错误码，并实现可独立测试的基础类型。此块不注册 `/ws/im`，也不替换现有游戏 WebSocket 的 `CheckOrigin`，因此合入后不改变 Phase 1 运行行为。

完成后，M2.0-B 只负责把已经验证的 JWT 与 Origin 组件接入游戏 WebSocket；M2.0-C 再建立 IM Hub 和真实路由。

## 3. 配置设计

### 3.1 Go 配置结构

```go
type Config struct {
    // 现有字段保持不变
    WebSocket WebSocketConfig
}

type WebSocketConfig struct {
    AllowedOrigins string
}
```

这里保留逗号分隔的原始字符串，不直接使用 `[]string`，避免 Viper 对 YAML 数组和环境变量字符串采用不同解码规则。标准化由 `realtime.ParseAllowedOrigins` 统一完成。

配置键：

| 来源 | 名称 |
|---|---|
| Viper | `websocket.allowedorigins` |
| 环境变量 | `TRPG_WEBSOCKET_ALLOWEDORIGINS` |
| `.env` 转发变量 | `WEBSOCKET_ALLOWED_ORIGINS` |

### 3.2 默认值

```text
http://localhost:5173,
http://127.0.0.1:5173,
http://localhost,
http://127.0.0.1
```

- `5173` 覆盖 Vue 开发服务。
- 无端口地址覆盖本地 Nginx 的 80 端口。
- HTTPS 或正式域名不提供猜测默认值，部署时必须显式配置。
- 默认值在代码和 `configs/config.yaml` 中保持一致。

### 3.3 Docker Compose

`.env.example`：

```dotenv
WEBSOCKET_ALLOWED_ORIGINS=http://localhost:5173,http://127.0.0.1:5173,http://localhost,http://127.0.0.1
```

`docker-compose.yml`：

```yaml
- TRPG_WEBSOCKET_ALLOWEDORIGINS=${WEBSOCKET_ALLOWED_ORIGINS:-http://localhost:5173,http://127.0.0.1:5173,http://localhost,http://127.0.0.1}
```

环境变量中只保存 Origin 白名单，不包含路径、Token 或其他凭据。

## 4. Origin 解析与匹配

### 4.1 数据类型

```go
type OriginSet struct {
    allowed map[string]struct{}
}

func ParseAllowedOrigins(raw string) (*OriginSet, error)
func (set *OriginSet) Allows(request *http.Request) bool
```

`OriginSet` 创建后只读，可安全被多个 WebSocket Handler 并发使用。

### 4.2 标准化规则

每个逗号分隔项执行：

1. 去除首尾空白，忽略空项。
2. 只允许 `http` 和 `https` scheme。
3. 必须包含 host，不允许用户名、密码、query 或 fragment。
4. path 只允许空字符串或 `/`，最终统一移除尾部 `/`。
5. scheme 与 host 转为小写；IPv6 继续保留方括号格式。
6. 默认端口标准化：`http:80` 和 `https:443` 分别移除。
7. 拒绝 `*`、`null`、相对地址和包含路径的 URL。
8. 去重后必须至少保留一个有效 Origin，否则返回配置错误。

示例：

| 输入 | 标准化结果 |
|---|---|
| `HTTP://LOCALHOST:80/` | `http://localhost` |
| `https://Example.com:443` | `https://example.com` |
| `https://example.com:8443` | 保持不变 |
| `https://example.com/app` | 拒绝 |
| `*`、`null` | 拒绝 |

### 4.3 请求匹配

- HTTP 请求没有 `Origin` 时允许，支持命令行和原生客户端；JWT 仍是必需条件。
- 有 `Origin` 时按同样规则标准化并精确匹配白名单。
- `Origin: null` 一律拒绝。
- 多值 Origin、解析失败或不在白名单时拒绝。
- 不依据 `Host`、`Referer` 或 `X-Forwarded-*` 自动放行，避免代理头伪造。
- Handler 在升级前先调用同一匹配器并返回稳定 JSON 错误；Upgrader 的 `CheckOrigin` 再使用该匹配器作为第二层防护。

M2.0-A 只测试 `OriginSet`；M2.0-B 才把它设置为游戏和 IM 共用 Upgrader 的 `CheckOrigin`。

## 5. 查询参数 JWT 鉴权

### 5.1 公共组件

```go
type AuthFailure string

const (
    AuthMissingToken AuthFailure = "missing_token"
    AuthInvalidToken AuthFailure = "invalid_token"
)

type AuthError struct {
    Failure AuthFailure
}

func AuthenticateQueryToken(rawToken, secret string) (*middleware.Claims, error)
```

设计原则：

- 公共层只区分缺失和无效，不决定 HTTP 状态或业务错误码。
- 现有 `middleware.ValidateToken` 继续负责签名、算法和过期时间校验。
- 游戏 Handler 在 M2.0-B 将两类失败映射为原有 `1500`、`1501`。
- IM Handler 在 M2.0-C 映射为 `1700`、`1701`。
- `AuthError.Error()` 不包含原始 Token 或底层 JWT 文本，避免日志泄露。
- `strings.TrimSpace(rawToken)` 为空视为缺失；非空但无效统一视为无效。

M2.0-A 不改变 JWT Claims，不引入设备 ID、Session ID 或 Token 吊销逻辑。

## 6. IM 消息契约

### 6.1 客户端信封

```go
type ClientMessage struct {
    Type      MessageType     `json:"type"`
    RequestID string          `json:"request_id,omitempty"`
    Data      json.RawMessage `json:"data,omitempty"`
}
```

```json
{
  "type": "ping",
  "request_id": "可选 UUID",
  "data": {}
}
```

规则：

- `type` 必填，首版最大 64 个 ASCII 小写字母、数字或下划线。
- `request_id` 如存在必须是标准 UUID，最大 36 字符。
- `data` 必须为空、`null` 或 JSON 对象；数组和标量拒绝。
- 顶层出现 `user_id`、`timestamp`、`seq` 或其他未知字段时拒绝，不做静默忽略。
- 单个 WebSocket 文本帧最大 8192 字节，不接受二进制业务消息。

### 6.2 服务端信封

```go
type ServerMessage struct {
    Type      MessageType     `json:"type"`
    RequestID string          `json:"request_id,omitempty"`
    Timestamp int64           `json:"timestamp"`
    Data      json.RawMessage `json:"data,omitempty"`
}
```

- `timestamp` 使用服务器 Unix 毫秒。
- IM 不使用连接级全局 seq；持久化 `seq` 位于未来的具体聊天消息数据中。
- 连接事件、presence 等非持久消息不伪造消息 seq。
- 序列化失败不发送部分消息，由 Hub 记录不含敏感数据的内部错误。

### 6.3 M2.0 基础消息

```go
const (
    MsgPing               MessageType = "ping"
    MsgPong               MessageType = "pong"
    MsgConnected          MessageType = "connected"
    MsgError              MessageType = "error"
    MsgConnectionReplaced MessageType = "connection_replaced"
)
```

数据结构：

```go
type ConnectedData struct {
    UserID       uint   `json:"user_id"`
    ConnectionID string `json:"connection_id"`
}

type ErrorData struct {
    Code    int    `json:"code"`
    Message string `json:"message"`
}

type ConnectionReplacedData struct {
    Reason string `json:"reason"`
}
```

`request_id` 只放在外层，不在 `ErrorData` 中重复编码。

### 6.4 预留消息名称

以下常量可以在对应里程碑再加入，M2.0-A 文档先保留名称，代码不提前声明未使用类型：

- M2.1：`presence`。
- M2.2：`chat_message`、`chat_ack`、`im_sync`、`im_sync_batch`、`conversation_updated`。
- M2.3：`group_updated`、`group_member_changed`。

## 7. 错误码与连接关闭

### 7.1 IM HTTP 握手错误

| 错误码 | HTTP | 场景 | 安全文案 |
|---|---:|---|---|
| `1700` | 401 | 缺少 Token | `missing token` |
| `1701` | 401 | Token 无效或过期 | `invalid token` |
| `1702` | 403 | 浏览器 Origin 不允许 | `origin not allowed` |

M2.0-C 注册路由后启用；M2.0-A 只冻结定义。

游戏通道继续保留 `1500—1507` 的现有含义，并新增：

| 错误码 | HTTP | 场景 | 安全文案 |
|---|---:|---|---|
| `1508` | 403 | 浏览器 Origin 不允许 | `origin not allowed` |

只有 `1508` 是新增契约；缺少或无效 Token、非法房间和无访问权仍返回原错误码。

### 7.2 IM 协议错误

| 错误码 | 场景 | 连接处理 |
|---|---|---|
| `1703` | JSON 或顶层信封非法 | 返回错误，连接保持 |
| `1704` | type、request_id 或 data 校验失败 | 返回错误，连接保持 |
| `1705` | 消息类型尚未支持 | 返回错误，连接保持 |
| `1706` | 后续业务处理器未注入 | 返回错误，连接保持 |
| `1707` | 内部编码或投递失败 | 记录日志并关闭连接 |

错误消息不回显原始 JSON、Token、数据库错误或内部堆栈。

### 7.3 WebSocket 关闭码

| 关闭码 | 场景 |
|---:|---|
| `1000` | 客户端正常断开 |
| `1001` | 服务端优雅停止 |
| `1009` | 消息超过 8192 字节 |
| `1011` | 服务端内部编码或不可恢复错误 |
| `4001` | 同一通道的新连接接管旧连接 |
| `4002` | 服务端发送缓冲区持续不可用 |

应用关闭码只用于已成功升级的连接；升级前错误继续使用 HTTP 状态和 JSON 错误码。

## 10. 风险与回退

- 本块不接入现有路由，出现问题可整体回退新增包和配置字段，不影响 Phase 1 请求路径。
- Origin 默认值在 M2.0-B 接线后会改变浏览器 WS 行为，因此接线前必须再次确认部署域名配置。
- 严格 IM 信封不会复用当前游戏 `ws.Message`，避免改变 Phase 1 客户端对未知字段的兼容方式。
- 不把 Origin 白名单当作认证手段；JWT 和后续资源权限仍是必要校验。

## 11. 完成后的评审点

M2.0-A 完成后需要核对：

1. 配置命名是否和当前 Viper、Docker Compose 约定一致。
2. Origin 规则是否覆盖开发服务、Nginx 和正式域名配置方式。
3. IM 信封是否没有混入游戏房间字段。
4. 错误码是否与现有 1500—1507 和后续社交模块范围冲突。
5. 全量回归是否证明 Phase 1 行为未改变。

评审通过后再开始 M2.0-B，不在同一提交中提前接入现有游戏 WebSocket。
