## 1. 目标

M2.5 在 M2.4 已冻结成员和 `turn_order` 的多人房间上，交付真正可运行、可恢复、可验收的多人回合闭环：

- 为多人房间建立 Redis 运行态 V2，保存全体玩家状态、当前行动者、行动抢占、截止时间、摘要和最近叙事。
- 当前行动者通过既有游戏 WebSocket 提交行动；Go 原子抢占后调用 Python AI，并向房间全部成员广播叙事、骰子和状态变化。
- 回合超时可自动跳过；断线不移除成员，重连从 REST 权威快照和游戏事件日志恢复。
- 房主可以暂停、恢复、手动存档、读档和结束游戏；读档与控制操作通过运行态世代隔离在途 AI 结果。
- 将游戏与 IM 的实时投递接入 Redis 跨实例总线，统一房间事件序号和补推日志，关闭 Phase 2 的多实例广播欠账。
- 提供多人游戏页面、回合队列、倒计时、行动输入、流式叙事和状态面板，并以至少三个账号完成真实浏览器验收。

## 3. 已有基线与兼容约束

- `game_rooms` 已持久化 `status`、`current_turn`、`round_number`、`turn_order`、`version` 和 `turn_timeout_seconds`；`room_players` 已冻结有效成员、角色和顺序。
- M2.4 开局目前只把 MySQL 房间切到 `playing` 并广播 `game_started`，尚未生成开场叙事或初始化多人 Redis 运行态；M2.5 必须把两者纳入同一可补偿协调流程。
- 单人运行态 V1 的 key、Lua、REST 和存档已经通过大量回归。多人实现使用独立 V2 类型和入口，不在单人 Lua 中堆叠条件分支。
- `/ws?token=&room_id=` 已允许多人有效成员订阅并支持同用户同房间新连接接管；多人行动继续复用该通道。
- 当前游戏 Hub 的 seq 和补推日志只存在单进程内存中，不能满足跨实例广播；在多人事件上线前必须迁移到 Redis 权威序号与日志。
- MySQL 继续作为房间生命周期和存档权威，Redis 是活动时间线权威。Redis 不可用时禁止推进回合，不使用 MySQL 猜测补写运行态。
- 旧 V1 单人存档只能恢复到单人房间；V2 多人存档只能恢复到原多人房间和相同冻结成员/角色集合。

## 4. 已确认的产品与实现决策

开发者已确认以下决策。除自动存档由建议的 10 个完整轮次调整为 5 个完整轮次外，其余均采用建议方案；M2.5-B 及后续实现不得自行改变。

| 议题 | 建议方案 | 主要取舍 | 决策回复 |
|---|---|---|---|
| 回合与轮次语义 | `current_turn` 是从 0 开始的行动槽水位；当前行动者为 `turn_order[current_turn % N]`；完整轮次为 `floor(current_turn / N)`，前端显示轮次从 1 开始 | 保持现有 `expected_turn` CAS；`round_number` 不再与多人 `current_turn` 等值 | 采用建议方案 |
| 自动存档频率 | 每完成 10 个完整轮次自动存档，即 `10 × 冻结成员数` 次成功行动/跳过后触发 | 符合“每 10 轮”产品语义，但比每 10 次玩家行动更稀疏 | 调整为每完成 5 个完整轮次自动存档，即 `5 × 冻结成员数` 次成功行动/跳过后触发 |
| 超时与在途 AI | 截止时间只约束玩家提交；行动抢占成功后暂停该回合计时，等待 AI 完成。房主暂停/读档/结束可轮换世代并取消在途行动 | 避免 AI 响应慢导致同一回合出现两个权威结果 | 采用建议方案 |
| 主动跳过权限 | 只有当前行动者可主动跳过；房主不能替其他玩家跳过，但可以暂停游戏；离线玩家等待计时器自动跳过 | 权限简单且避免房主代替玩家操作，代价是离线时最多等待一个超时周期 | 采用建议方案 |
| 开局后断线与退出 | 成员名单永久冻结到游戏结束；断线不改变顺序，到其回合仍计时并自动跳过；M2.5 不提供开局后离开/踢人 | 存档和角色状态稳定，但中途退团只能由房主结束整局 | 采用建议方案 |
| 游戏控制权限 | 仅房主可暂停、恢复、手动存档、读档和结束；所有有效成员可读状态与存档列表，只有当前行动者可行动/跳过 | 复用现有房主控制模型，成员拥有完整可见性但无时间线控制权 | 采用建议方案 |
| 结束条件 | 房主可手动结束；AI 显式 `end_game`，或全体角色状态都存在合法 HP 且均≤0 时自动结束；结束后不可恢复，只能读取历史和存档 | 自动覆盖剧本终点与全灭，但需要严格校验 AI 结构化效果并避免缺失 HP 时误判 | 采用建议方案 |
| 流式叙事一致性 | chunk 以 `request_id` 作为临时缓冲；只有 `narrative_complete` 后写入正式时间线。世代失效时广播 `action_cancelled`，客户端丢弃对应临时缓冲 | 保留流式体验，同时避免暂停/读档后把未提交文本当成权威历史 | 采用建议方案 |
| 前端页面 | 新增 `/game/multi/:roomId`，复用骰子、状态卡等展示组件，不在 `GamePlayView.vue` 内混入大量单双人分支 | 多一个路由和页面，但边界清晰、单人回归风险更低 | 采用建议方案 |

## 5. 权威状态与回合语义

### 5.1 多人运行态 V2

V2 快照至少包含：

```json
{
  "version": 2,
  "room_id": 41,
  "status": "playing",
  "generation": "uuid",
  "current_turn": 0,
  "round_number": 0,
  "turn_order": [7, 8, 9],
  "current_actor_id": 7,
  "deadline_at": "2026-09-21T16:00:00.000Z",
  "players": [
    {
      "user_id": 7,
      "character_id": 101,
      "player_state": {"hp": 12, "san": 45},
      "items": [],
      "buffs": []
    }
  ],
  "summary_memory": "",
  "recent_messages": []
}
```

- `generation` 标识当前时间线；暂停、读档和结束都使旧世代无法提交。
- `current_turn` 是行动 CAS 水位，成功行动和跳过都只推进一次。
- `current_actor_id` 必须能由 `turn_order` 和 `current_turn` 推导，快照解码时交叉校验。
- `deadline_at` 只在 `playing` 且没有行动抢占时存在；`paused/ended` 或 AI 推理中为空。
- 玩家状态按 `user_id` 隔离，道具和 Buff 不能继续复用单人所有者假设。

### 5.2 Redis key 与原子脚本

沿用 `room:{room_id}:*` 前缀，新增或明确以下 V2 数据：

- `runtime_version`、`status`、`generation`、`turn`、`turn_order`、`deadline_at`。
- `player:{user_id}`、`player:{user_id}:items`、`player:{user_id}:buffs`。
- `rounds`、`summary`、`action_results`、`pending_auto_saves`。
- `action_lease`：当前世代、回合、行动者、请求 ID、指纹和抢占时间。
- 全局 `game:turn_deadlines` ZSET：score 为毫秒截止时间，member 含房间 ID 与世代/回合令牌。

Lua 边界：

1. `InitializeMultiplayerRoom`：原子写入完整 V2 provisional、全体玩家状态和开场叙事，此时不可行动且没有截止任务。
2. `ActivateMultiplayerRoom`：按同一 generation 将 provisional 激活为 playing，并原子写入首个截止时间和调度任务。
3. `AcquireMultiplayerAction`：校验 playing、世代、回合、当前行动者、截止时间、请求幂等和无抢占；成功后写 `action_lease` 并移除截止任务。
4. `CommitMultiplayerAction`：校验 lease 与世代，应用限定玩家效果，保存幂等结果，推进回合，写下一个截止任务；必要时生成 V2 自动存档快照。
5. `SkipMultiplayerTurn`：校验当前回合和权限/超时令牌，推进且只推进一次；与行动抢占竞争时只能有一方成功。
6. `TransitionMultiplayerStatus`：暂停/恢复/结束时轮换世代、清理 lease 和截止任务；恢复生成新截止时间。
7. `RestoreMultiplayerRoom`：原子替换全部 V2 key，状态固定为 paused，不恢复旧绝对截止时间。

所有 V2 key 使用同一 TTL 并在有效读写时续期。房间 ended 后清除活动截止任务，但保留短期只读快照供客户端收尾；MySQL 存档和房间状态仍是长期权威。

### 5.3 启动协调与失败补偿

不新增 MySQL `starting` 状态，使用短期 Redis 启动租约避免重复开局：

1. 房主携带 `expected_version` 调用既有 `/rooms/{id}/start`。
2. 获取 `room:{id}:start_lease`，读取并校验仍为 waiting 的冻结候选快照。
3. Python 生成面向全队的开场叙事；Go 初始化状态为不可行动的 V2 provisional runtime。
4. MySQL 事务再次校验版本、成员、角色和准备状态，写入 `turn_order` 并切到 playing。
5. Redis 按同一 generation 激活 runtime、创建首个 deadline；随后发布 `game_started`、开场叙事和 `turn_start`。
6. MySQL 提交前失败：删除 provisional runtime，房间保持 waiting。MySQL 已提交但激活结果不确定：进入安全暂停并由幂等 reconcile 完成，不允许客户端行动。

启动租约只防重复协调，不替代 MySQL `expected_version`。任何失败都不得广播 `game_started`。

## 6. 多人 AI 与行动提交

### 6.1 Python 内部契约

扩展内部行动请求，保留现有单人字段并增加多人参与者：

```json
{
  "room_id": 41,
  "user_id": 7,
  "action": "检查门后的脚印",
  "script_id": 9,
  "character_id": 101,
  "participants": [
    {"user_id": 7, "character_id": 101},
    {"user_id": 8, "character_id": 102}
  ]
}
```

- Python 从 Redis 读取全体参与者状态并组装队伍上下文；当前行动者仍单独标记。
- Function Calling 只能修改 `participants` 内用户；非法目标、重复骰子、未知效果或越界数值使整次推理失败。
- 新增 `end_game` 结构化效果时只返回原因和结局摘要，最终结束判定仍由 Go 校验并提交。
- 单人请求不带 `participants`，继续走原 V1 上下文和效果约束。

### 6.2 服务端流程

1. 严格解析 `game_action`，从连接推导 room/user，不信任客户端身份字段。
2. 查询已提交请求缓存；完全相同的重试返回原结果而不重复调用 AI 或广播。
3. Redis 原子抢占当前回合；非当前行动者、旧回合、超时后到达或已有 lease 均返回稳定错误。
4. 向 Python 流式端点发起带超时和可取消 context 的请求；chunk 按请求 ID 广播给全房间。
5. Go 重新校验骰子、状态效果和结束效果；Redis 原子提交，只有提交成功才广播骰子、状态、complete 和下一个 `turn_start`。
6. AI/网络失败时释放同一 lease 并恢复剩余或新的提交截止时间；失败只通知发起者，不推进回合。
7. 世代失效或服务关闭导致提交失败时广播 `action_cancelled`，所有客户端丢弃该请求的临时 chunk。

## 7. 超时调度与跨实例实时总线

### 7.1 回合调度

- 每个实例运行轻量 deadline worker，从 Redis ZSET 领取到期任务；领取和 `SkipMultiplayerTurn` 使用令牌 CAS，多个实例竞争时只有一个推进。
- worker 崩溃不会丢失任务；未处理 member 仍留在 ZSET 或在短租约到期后重新可见。
- 跳过成功发布 `turn_skip {user_id,current_turn,reason}`，随后发布下一 `turn_start`。
- 服务启动不扫描 MySQL 猜测 deadline，只恢复 Redis 中仍有效的 V2 任务。

### 7.2 全局事件序号、日志与 Pub/Sub

新增 Redis `RealtimeBus`，同时承载游戏房间事件和 IM 用户事件：

- 发布端先通过 Lua 为 `room_id` 分配全局 seq，将完整服务端信封写入有界日志，再 publish 同一信封。
- 所有 Go 实例订阅后只向本实例连接投递，不能二次分配 seq。
- `sync` 从 Redis 日志按 `since_seq` 补推；水位早于有界日志时返回 `snapshot_required`，客户端重新拉取 REST 权威状态。
- IM 用户事件通过用户 topic 跨实例投递；分布式连接所有权与控制 topic 用于跨实例 4001 接管。
- Redis 不可用时拒绝会推进权威游戏状态的操作；聊天仍保持 MySQL 持久化权威，但实时投递降级并由 `im_sync` 补齐。

## 8. REST、WebSocket 与错误码

### 8.1 REST

新增：

| 方法 | 路径 | 权限 | 用途 |
|---|---|---|---|
| `GET` | `/api/v1/games/{roomId}/state` | 有效冻结成员 | 获取 V2 安全快照、当前行动者、截止时间和最近叙事 |
| `POST` | `/api/v1/games/{roomId}/skip` | 当前行动者 | 主动跳过，携带 `request_id`、`expected_turn` |

扩展既有 `/games/{roomId}/pause|resume|saves|load|end`：单人分支保持原权限和 V1 行为；多人分支按第 4 节决定执行。所有写操作必须校验活动世代/回合或房间状态，不只依赖页面快照。

### 8.2 游戏 WebSocket

客户端继续使用 `game_action` 和 `sync`。服务端新增/明确：

- `game_runtime_snapshot`
- `action_started`
- `action_cancelled`
- `turn_start`
- `turn_skip`
- `game_status_changed`
- `game_ended`
- 复用 `narrative_chunk`、`narrative_complete`、`dice_roll`、`status_update`、`sync_batch` 和 `error`

所有多人事件携带 `room_id`、全局 `seq`、`generation`；回合相关事件还携带 `current_turn` 和 `current_actor_id`。客户端只接受更高 seq，并在 generation 改变时清空旧的临时叙事缓冲。

### 8.3 多人错误码

继续使用 `1900—1999`：

| 代码 | HTTP/WS | 场景 |
|---:|---:|---|
| `1920` | 503 | 多人运行态或实时总线不可用 |
| `1921` | 409 | 旧世代、旧回合或状态冲突 |
| `1922` | 403 | 当前用户不是行动者或无控制权限 |
| `1923` | 409 | 当前回合已有行动在处理 |
| `1924` | 409 | 同一请求 ID 被不同内容复用 |
| `1925` | 409 | 存档版本、房间或冻结成员不兼容 |
| `1926` | 400 | 非法多人行动、跳过或状态请求 |
| `1927` | 503 | 多人 AI 推理不可用 |
| `1928` | 500 | 多人回合内部错误 |

对非成员继续统一表现为 `1901 room not found`，不泄露房间存在性。

## 9. 存档、读档与生命周期

- V2 `redis_snapshot` 包含全体玩家状态和准确的回合水位；摘要与最近消息继续使用现有独立列，不重复编码。
- 多人自动存档按已确认决策每完成 5 个完整轮次触发；跳过同样推进槽位并计入轮次水位。
- 自动存档由 Redis 提交/跳过脚本产生待持久化快照，再由 Go 幂等写入 `game_saves`；MySQL 唯一性沿用房间+轮次的幂等规则并补充多人回归。
- 手动存档只捕获已提交状态；存在 `action_lease` 时先暂停并取消在途行动，不能保存半个 AI 结果。
- 读档必须先暂停，校验 V2、room ID、冻结成员/角色和 turn order 后原子恢复；恢复后保持 paused，显式 resume 才生成新的 deadline。
- 暂停、读档、结束都会取消 deadline、轮换 generation 并使旧 AI 结果无法提交。
- 结束清理活动 lease/deadline，持久化最终 `current_turn/round_number`，广播结局；历史和存档保持只读。
- `gaming` 只在用户的 IM presence 为 online，且 MySQL 显示其为至少一个 `playing` 多人房间的冻结成员时产生；暂停或结束后回落为 online，IM 离线仍为 offline。开始、恢复、暂停和结束提交后向好友推送重算结果。

## 10. Vue 设计

- 新增 `/game/multi/:roomId` 和多人 Store；大厅收到 `game_started` 后导航到该页面。
- 首屏先拉取 `/games/{roomId}/state`，再连接游戏 WS；使用 snapshot 的 seq/generation 作为实时合并基线。
- 页面展示房间成员、角色、当前行动者、轮次、倒计时、连接状态、叙事流、骰子和每个角色的公开状态。

## 12. 验收标准

- 非当前行动者无法抢占；并发行动、超时、暂停、读档和结束竞争时只有一个权威结果推进水位。
- 相同请求重试不重复调用 AI、不重复应用效果、不重复广播完成事件；请求 ID 换内容被拒绝。
- 三个以上客户端看到相同 seq、叙事、骰子、状态、当前行动者和 deadline。
- AI 中途失败不推进；暂停/读档后旧 AI 结果和旧 chunk 不进入权威时间线。
- 超时任务在双实例竞争、进程重启和重复领取下最多跳过一次。
- 跨实例房间/IM 事件可达；同通道新连接能跨实例接管旧连接；断线按 Redis 日志或 REST 快照恢复。
- V2 手动/自动存档可恢复全体玩家状态和准确行动者；V1 单人存档继续读取。
- 断线成员不被移除，到其回合按决策自动跳过；重连后恢复同一成员和角色。
- 单人游戏、好友、私聊、群聊和多人大厅现有测试全部继续通过。
- OpenAPI 路由契约、Go test/vet/build、Python、Vue、迁移、MySQL 8.4、Compose 和 targeted race 全部通过。

## 13. 主要风险与控制

| 风险 | 控制 |
|---|---|
| AI 流式输出先于权威提交 | request ID 临时缓冲；complete 才落正式时间线；世代失效发 cancelled |
| 定时器与行动同时推进 | deadline token + Lua CAS；抢占成功即移除 deadline |
| MySQL 已开局但 Redis 激活不确定 | provisional generation、幂等 reconcile、安全暂停，不猜测继续行动 |
| 多实例生成重复 seq 或重复广播 | Redis 单点分配完整信封；实例只转发，不重编号 |
| Pub/Sub 丢消息 | 先写有界 Redis 日志再发布；过期则 REST snapshot_required |
| 多角色效果越权 | Python 白名单收集 + Go 二次校验 + Lua 只允许冻结玩家 key |
| V2 破坏 V1 单人存档 | 独立类型、严格 version 分派、单人全量回归 |
| 读档恢复旧 deadline | 快照不恢复绝对截止时间；保持 paused，resume 生成新 deadline |
| 断线玩家阻塞全队 | 固定超时自动跳过；首版不改变冻结 roster |
