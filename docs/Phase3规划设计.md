## 1. 目标与范围依据

Phase 3 的目标是让现有单人和多人跑团能够稳定进行长剧情，允许玩家在规则内使用自己的角色，并在关键剧情节点共同决策。

范围依据为 [需求文档](./需求文档.md) 中 M-04、M-05、C-05、MP-03 及已确认的裁剪决策，结合 [M2.5 实施方案](./M2.5实施方案.md) 和当前代码。保留 M3.1“记忆增强”和 M3.2“体验优化”的原编号；增设 M3.0 准备工作和 M3.3 阶段验收，便于跟踪交付。

| 范围 | 安排 | 说明 |
|---|---|---|
| 关键事件持久化、上下文注入 | M3.1 必做 | 接通已有 `trigger_event`，让重要事实可追溯 |
| 较早历史的语义记忆 | M3.1 必做 | 在房间与有效时间线内召回，支持重建索引 |
| 自定义角色 | M3.2 必做 | 覆盖预设微调和模板内新建，保持开局后阵容冻结 |

## 5. M3.1：记忆增强

### 5.1 产品行为

玩家可查看当前房间的关键剧情事件及发生位置。AI 在较长游戏后仍能依据已发生的事实回答 NPC 关系、已取得物品、关键选择和当前目标；未提交的叙事、其他房间的信息、读档后被撤销的未来不能进入上下文。

“不可遗忘”表示关键事件有持久化来源且不会仅因摘要压缩被删除，不表示每次无限量注入模型，也不保证模型绝不出错。当前数值状态以服务器运行态为准，记忆中的历史 HP/物品不能覆盖现值。

### 5.2 M3.1-A：时间线与持久化

建议新增的逻辑实体如下，名称与最终 SQL 在实施方案冻结：

| 实体 | 最小职责 | 关键约束 |
|---|---|---|
| `game_timelines` | 当前分支、父分支及读档分叉点 | 房间归属明确；能计算祖先可见水位 |
| `game_action_records` | 已提交开场/行动/跳过、正式叙事、效果、来源请求和提交位置 | 同一次提交只归档一次；禁止归档临时 chunk；系统事件同样分配可排序位置 |
| `key_events` | 已校验事件、来源行动、事件类型与重要度 | 同来源的事件序号唯一；只读有效时间线 |
| `memory_index_jobs` | 索引任务、来源版本、重试与处理结果 | MySQL 中持久化任务，幂等重试，支持重建 |

必须区分两个标识：

- `generation` 继续用于使旧行动/worker 失效，暂停、恢复等操作可能改变它。
- `timeline_id` 表示剧情分支，普通暂停/恢复不改变它；读档建立新分支并记录父分支和保存水位。不能只按当前 generation 检索记忆，否则一暂停就会忘掉之前的事实。

例如在行动水位 20 存档，继续到 30，再读回 20：新分支继承旧分支不超过 20 的历史；21—30 保留审计但不再可见。再次读档也必须沿祖先链计算可见范围，不能只用 `room_id + turn <= 当前回合`，因为不同分支可能复用相同回合号。提交位置应支持同一行动槽上的投票等事件顺序，不能只依赖 WS `seq`。

建议的写入流程：

1. 在 Redis 行动原子提交中一并登记待归档记录，包含服务端确认的请求、时间线、正式结果及提交标识；AI 仅返回候选效果。
2. Go 将待归档记录幂等写入 MySQL，并在同一 MySQL 事务登记后续索引任务；成功后确认 Redis 待办。
3. 进程重启、重复领取或响应丢失只补归档，不重新调用 AI，也不重复推进。
4. 待归档失败时展示可恢复错误并阻止依赖该持久化水位的后续推进/新格式存档；读档和结束必须保留或完成旧待办，不能随 generation 清理而丢失它们。

这仍不是 Redis 与 MySQL 的分布式事务。M3.1-A 必须明确 Redis 持久化配置、未落 MySQL 的故障窗口、积压上限、告警与恢复办法。暂定策略为“归档未确认前不确认记忆持久化成功”；是否要求更强的零丢失保证留待决策，不用“最终一致”笼统代替故障处理。

A 的验收：同请求重放唯一、提交后进程终止可补写、两个 worker 不重复归档、暂停不丢历史、多次读档无未来事实、不同房间不互见、待办未确认时无法形成宣称完整的新存档。

### 5.3 M3.1-B：关键事件、摘要和上下文

- 先将已有 `trigger_event` 接入服务端校验与归档；角色死亡等可由状态差值确认的事件使用确定性规则补充，重大抉择由 AI 提议再校验来源和字段。
- 不因普通叙事文本包含“死亡”“完成”等词直接改变游戏状态；持久化来源必须是已提交结果。
- 用已归档但尚未总结的消息生成摘要，记录 `summary_through_position`。异步结果回写必须校验房间、时间线和来源水位，防止旧任务覆盖新摘要。
- 暂定按每 5 个有新增正式叙事的行动提交检查摘要；跳过不应单独触发空摘要。该周期独立于多人每 5 个完整轮次自动存档。
- 近期上下文暂沿用当前最多 10 条消息的兼容口径；实施时明确消息、用户/AI 对话对、行动槽和完整轮次的区别，不把“10 条”自动扩大为“10 轮”。
- 上下文设置总预算和各部分预算：服务器当前状态/规则、关键事实、近期记录、摘要、历史召回、剧本 RAG。超预算先缩减低相关历史，不能挤掉当前行动和核心约束。
- 摘要失败保留旧摘要并重试；无关或重复 `trigger_event` 不无限扩张提示词。原始归档仍保留，玩家可以查来源。
- 摘要水位落后于近期窗口时，对尚未总结的记录做有预算的补齐并标记降级，不能静默留下上下文缺口；摘要、检索结果与玩家背景均是参考数据，不得覆盖系统指令或授权边界。
- 增加房间内只读事件列表。首版不提供玩家任意编辑世界事实；纠错和人工置顶作为后续独立决策。

B 的验收：摘要跨周期实际更新、失败不丢事实、长文本有预算、来源可追溯、事件列表权限与游戏房间一致、读档后摘要和事件都回到正确位置。

### 5.4 M3.1-C：语义记忆

- MySQL 行动与事件记录为权威，Milvus 仅为可重建索引；与剧本向量使用独立 collection/命名空间。
- Python 负责 embedding/检索，Go 负责可见性与持久化协调。内部任务必须带服务端生成的房间、来源记录和时间线约束。
- 检索先约束房间与可见分支范围，再计算相似度/MMR；返回后按权威来源二次核验。禁止先跨房间召回后直接将结果注入上下文。
- 存储来源记录 ID、内容摘要/哈希、embedding 模型标识及索引版本；重试、删除或模型更新可按版本重建，不能把不同维度向量混入旧索引。
- 召回较早事实并去除与近期消息、关键事件的重复；Top-K、预算及相关性阈值通过固定评估集选择，不在规划阶段绑定未经测试的数字。
- Milvus 故障或超时回退到关键事实、摘要和近期上下文，仍可行动；记录降级状态和延迟，不把检索失败当作“没有历史”。
- 索引滞后以 MySQL 关键事实补充。删除房间/脚本相关数据时定义关联清理和重试；失效分支即使尚未删向量，也必须在读取侧不可见。

C 的验收：跨房间/跨分支泄漏为零；重复任务不增重复向量；Milvus 恢复后任务可追平；重建不改变事实源；索引关闭时行为回到基本记忆路径。

### 5.5 存档兼容与 M3.1-D 验收

建议新格式显式区分 `schema_version` 与 `mode`，包含时间线/保存水位、摘要来源和后续角色快照。最终版本号在 M3.1-A 冻结；旧 V1/V2 只通过解码适配读取，不重写旧存档原始 JSON。

- 旧存档没有完整历史引用时，只恢复原有摘要、状态和近期消息，明确标注缺少更早来源；不能从当前房间另一路未来历史补齐它。
- 读档建立新的运行 generation 和可追溯剧情分支，继续保持 paused；旧异步摘要/索引结果不能污染新分支。
- `memory_enabled=false` 的开关可以停用检索或注入，但不能让旧程序误读新存档；降级应用版本的兼容范围需单独验证。

验收集至少包含三类场景：NPC 关系与线索、物品去向与角色变化、读档后选择另一分支。每类保留来源事实、问题、期望引用、禁用事实和模型回答。

建议先用至少 30 个可重复问题评估基线与新实现：跨房间/分支泄漏 0，取消行动入库 0，规定场景事实命中率目标 ≥90%（由开发者确认门槛）。确定性测试覆盖 100 次已提交行动的截断与恢复；真实 AI 长局单独安排并预先限定调用预算，不用 fixture 的 100 轮代替真实模型质量结论。

## 6. M3.2：角色、投票与 Web 体验

### 6.1 M3.2-A：自定义角色

建议首版采用“个人角色草稿 + 房间引用版本 + 开局不可变快照”：

- 支持从预设复制微调，以及在同一规则模板内新建。编辑只影响本人的草稿，不能修改剧本共享预设或他人角色。
- 模板列出允许字段、类型、取值范围、总点数/技能预算和初始装备规则；数值范围在实施方案确认，服务端为最终校验者，AI 不负责批准任意超规格属性。
- 房主创建房间时决定是否允许自定义角色；建议默认关闭。允许后，玩家提交角色版本，房主确认后才可准备。
- 修改已选择角色必须产生新版本并撤销相关准备/确认；有过期 `room.version` 的提交失败并刷新大厅。单人开始前本人确认即可。
- 开局冻结全队实际角色内容及来源版本。角色草稿后续修改/删除，不得影响进行中的游戏、历史记录或旧存档。
- 现有 `character_id` 校验、角色唯一选择、Python 角色加载和 V2 阵容比较都要一起扩展；不能只加一张个人角色表就绕过现有剧本归属检查。
- 游戏中不开放重新分配属性、换角或改变冻结顺序。角色背景作为不可信参考文本处理，不能改变系统规则或取得其他房间数据。

交付拆为规则与兼容设计、后端与迁移、Vue 编辑/审批/选择、存档回归四个提交块。

验收：非法点数/装备拒绝、他人草稿不可写、双端编辑版本冲突、编辑后 ready 撤销、批准版本与开局快照一致、删除草稿后读档仍可用、旧预设房间不受影响。

### 6.2 M3.2-B：剧情投票

暂定产品规则：

| 议题 | 建议规则 |
|---|---|
| 发起 | AI 在正式提交结果中提议，房主确认；房主也可手工发起。AI 未提交的 chunk 不能开启投票 |
| 参与者 | 当前冻结真人成员，AI 不投票；单人不展示投票 |
| 选项 | 单选，2—6 个明确选项；首版不可改票，不新增自由文本选项 |
| 截止 | 默认 60 秒，配置范围建议 30—180 秒；离线成员保留投票资格，到期未投视为弃权 |
| 结算 | 全员已投或截止到达时结算；唯一最高票且至少一张有效票则通过；平票/全弃权则无结果 |
| 无结果 | 房主可重新发起或取消；不由 AI 随机选择，也不默认为房主选择 |
| 展示 | 投票中仅显示已投人数，结束后显示各选项汇总；不承诺服务端匿名投票 |
| 回合 | 投票期间禁止行动/跳过并挂起行动 deadline；结算后仍是同一当前行动者，重新给予完整行动时限 |
| 控制冲突 | 暂停、手动存档、读档、结束会取消未完成投票；恢复不自动续投，不恢复过期选票 |

技术边界：

- 保留房间 `waiting/playing/paused/ended` 主状态，增加投票子状态，建议 `open → resolved / no_result / cancelled`；同房间最多一个活动投票。
- 发起时要求无在途行动；必须与行动抢占、deadline worker 使用同一原子协调边界。若需要 MySQL/Redis 双侧落地，用创建/结算令牌与可恢复待办保证不会只锁住游戏却没有可读投票。
- 投票和选票持久化，`(vote_id, user_id)` 唯一；携带请求 ID、投票版本、时间线和 generation，重复提交/跨实例结算都幂等。
- 暂停后迟到投票、读档前旧投票、超过截止的选票均拒绝；重启后能确定恢复活动投票或完成取消/结算，不能重启一个完整 60 秒窗口。
- WebSocket 推送投票变化、关闭与取消，沿用房间全局 seq；REST 快照包含活动投票，事件缺口后可恢复。
- 最小闭环将结果写入正式系统事件并注入下一次 AI 行动，不额外消耗玩家行动槽。若未来要投完自动生成叙事，须另行定义生成租约、失败重试与计费规则。
- 读档后的可见投票结果遵循 M3.1 分支水位；旧分支结果只作审计。投票中的自动存档不应额外推进或制造存档轮次。

验收：三人正常投票、离线弃权、平票、全弃权、重复/迟到提交、他人越权、双实例同时结算、超时与行动竞争、暂停/存读档/结束取消、重启与断线快照恢复；结果最多写入一次且回合不多推进。

### 6.3 M3.2-C：Web 使用体验

- 游戏页适配桌面、平板和手机浏览器，建议检查 360、768、1440 像素宽度。覆盖输入法/软键盘、长叙事、状态侧栏与投票弹层。
- 明确区分“等待轮到我”“生成中”“投票中”“已暂停”“连接恢复中”“已结束”，禁用控件给出原因。
- 倒计时以服务端 deadline 为准；标签页后台恢复后校正，前端归零不直接推进服务器回合。动画服从减少动态效果偏好。
- 错误恢复入口、失败重试、存档完成反馈、读档取消提示可操作；重要按钮支持键盘焦点，状态不只靠颜色。
- 关键事件列表支持定位来源；长列表优先分页/按需渲染，是否虚拟化由数据量和性能实测决定。

完成标准：三种视口的核心操作无横向溢出或遮挡，键盘可完成关键流程，断线与失败状态能明确恢复；本块不交付原生 App 或小程序。

## 7. 接口、存储与职责规划

以下是候选能力路径，尚不是已提供的 API；每块实现时同步 OpenAPI、Go DTO、Python 内部协议和 Vue 类型，并分配未占用错误码。

| 能力 | 候选接口 | 权限与说明 |
|---|---|---|
| 事件列表 | `GET /api/v1/games/{roomId}/events` | 单人房主/多人有效冻结成员；服务端推导可见分支，游标分页 |
| 个人角色 | `/api/v1/characters`、`/api/v1/characters/{id}` | 本人增查改删，版本冲突显式返回 |
| 房间角色确认 | 房间成员下的角色提交/确认操作 | 玩家提交自己的版本、房主确认，waiting 状态限定 |
| 投票状态/发起 | `GET/POST /api/v1/games/{roomId}/votes` | 成员读取、房主发起 |
| 投票提交/取消 | `/votes/{voteId}/ballots`、`/votes/{voteId}/cancel` | 合格成员投票、房主取消；完整前缀沿用房间路径 |
| 索引/摘要任务 | Go ↔ Python 内部 HTTP | 内部密钥校验、来源版本、超时、幂等；不开放给浏览器 |

Go 保留业务鉴权和提交权，Python 负责候选事件、摘要、embedding 与检索，Vue 展示权威快照。新增 SQL 延续顺序迁移与应用层关系校验，不恢复已移除的外键策略。迁移、索引和新存档版本必须配套升级计划，不能修改 001—017 的已执行内容。

## 8. M3.3：验收、发布与回退

### 8.1 验收矩阵

| 领域 | 自动化门禁 | 真实环境证据 |
|---|---|---|
| 基础回归 | 单人/多人、好友/私聊/群聊、鉴权与旧存档 | 真实脚本上传解析 → 开局 → 行动 → 存读档 → 结束 |
| 记忆 | 幂等归档、跨分支/房间隔离、摘要 CAS、索引重试 | 真实 AI + Milvus 的长局事实召回与读档分叉 |
| 角色 | 属性预算、归属、版本与快照 | 三人自定义/预设混合开局，草稿变更后旧存档可恢复 |
| 投票 | 选票唯一、双实例结算、截止与控制竞争 | 三个会话分连两个 Go 实例，断网/重启/恢复仍一致 |
| 工程 | Go test/vet/race、Python、Vue test/build、迁移与 OpenAPI、Compose | 真依赖启动、升级存量库、日志/任务恢复和关闭新功能 |
| Web | 核心交互回归、权限与错误提示 | 手机软键盘、窄屏、后台切换、键盘操作、长叙事 |

“双实例”指两个 Go 服务实例共享同一个 Redis/数据库部署，不是把两个独立 Redis 数据库当作同一运行态。Redis 高可用/Cluster 是另一个运维议题。

### 8.2 性能与质量口径

- 沿用需求中的待验目标：AI 首 Token P95 <3s、完整回复 P95 <30s、WS 端到端 P99 <200ms；记录测量起止点、并发量、样本量、模型、网络与冷/热缓存。
- 分别记录鉴权、记忆检索、AI 等待和广播耗时，保留失败/超时样本；指标未达标时给出实测值和原因，由开发者决定修复或明确接受偏差，不暗改目标。
- ≥100 并发房间的服务端压测先使用受控 AI fixture；真实模型并发另设调用预算与限额，不能把 fixture 压测当作真实 AI 吞吐证明。
- 记忆正确率使用固定评估集，分别报告检索是否命中和最终回答是否正确；人工审阅不能仅由同一模型自评分代替。

### 8.3 升级与回退

建议按“备份并记录迁移水位 → 增量迁移 → 部署支持新旧协议的代码 → 新房间灰度启用 → 回归 → 扩大启用”实施；具体脚本在开发阶段生成。

- 活动旧房间默认保持原能力；新房间按冻结的功能配置开启。旧房间升级必须有快照和转换验证。
- 分别控制记忆注入、自定义角色和投票功能；关闭新建入口不能破坏已开始游戏中仍需恢复的状态。
- 首选应用功能降级及向前修复。回滚旧二进制前先验证其能否读取新房间/存档；禁止直接回退并让不认识新格式的代码接管活动房间。
- 数据库回退不得默认删表/清空已产生的角色、事件或投票；先停相关写入、保全数据，使用经过演练的恢复方案。

完成标准：必做分块达到各自标准；目标环境端到端和升级恢复通过；没有未处置的跨房间泄漏、重复推进、读档串线或状态丢失问题；验收报告明确保留的非阻塞问题。Phase 1 仍未验完的事项不能随 Phase 3 合并自动关闭。
