## 1. 阶段目标

Phase 2 的目标是完成“好友关系 → 私聊/群聊 → 多人房间 → 多人 AI 跑团”的社交闭环，同时复用 Phase 1 已完成的认证、剧本、AI 推理、Redis 游戏运行态、存读档和 WebSocket 游戏事件能力。

本阶段拆分为六个里程碑：

1. M2.0：契约与实时通信基础。
2. M2.1：好友与在线状态。
3. M2.2：私聊与可靠消息。
4. M2.3：群组与群聊。
5. M2.4：多人房间与等待大厅。
6. M2.5：多人回合、前端闭环与验收。

## 2. 范围边界

### 2.1 本阶段包含

- 通过用户 ID 或用户名查找用户并发送好友申请。
- 好友申请列表、接受、拒绝、删除好友和在线状态。
- 好友私聊、群组管理、群聊、历史消息和断线补推。
- 4—6 人多人房间、邀请或房间码加入、选角、准备和房主开局。
- 多人回合队列、行动权限、AI 流式叙事广播、骰子与状态更新广播。
- 多人存档、读档、暂停、恢复和结束游戏。
- Vue 好友、会话、群组、等待大厅和多人游戏界面。
- 公共 REST OpenAPI、WebSocket 契约文档、自动化测试和真实联调记录。

### 2.2 本阶段不包含

- 黑名单、陌生人私聊、消息撤回、编辑、已读回执和文件消息。
- 同账号多设备同时在线和跨设备实时状态同步。
- 群公告、复杂群权限、自定义表情和全文消息搜索。
- 投票决策、自定义角色、旁观模式和移动端专项适配。
- 跨区部署、超大群和海量历史消息归档。
- Phase 3 的关键事件持久化与语义记忆。

## 4. 核心架构决策

### 4.1 游戏与 IM 使用两个 WebSocket 入口

- 游戏通道继续使用 `/ws?token=<JWT>&room_id=<roomId>`。
- 新增用户级 IM 通道 `/ws/im?token=<JWT>`。
- IM 通道按用户维护一个活动连接，不要求用户先进入游戏房间。
- 同一用户在同一通道建立新连接时，由新连接接管并关闭旧连接；不实现多设备消息同步。
- 同一客户端可以同时保持一条 IM 连接和一条游戏房间连接，这不视为多设备在线。
- 两个通道可以复用消息编码、心跳、错误和连接生命周期工具，但不共享业务订阅状态。

这样可以保持 Phase 1 游戏客户端兼容，并避免为了聊天功能一次性重写已完成的游戏 Hub。统一为单连接多主题订阅可在 Phase 2 稳定后单独评估。

### 4.2 MySQL 是消息与关系权威

- 好友关系、群成员、会话成员和消息先写 MySQL，成功后再实时推送。
- 消息以会话内单调 `seq` 分页和补推，不依赖 WebSocket 进程内序号作为持久化依据。
- Redis 只保存在线状态、短期幂等结果、跨实例事件和游戏运行态。
- 离线用户重连后从 MySQL 按 `since_seq` 补取，因此不再维护一份可能与数据库不一致的 Redis 离线消息副本。

### 4.3 不使用数据库外键

- Phase 2 新表不创建 `FOREIGN KEY` 约束。
- 不创建仅用于满足外键要求的索引。
- 只保留实际查询、排序、唯一性和幂等需要的业务索引。
- 关联存在性、成员权限、删除清理和一致性由 Service 事务显式保证。
- 所有迁移同时覆盖空库执行、已部署升级、重复执行防护和结构校验测试。

### 4.4 消息投递采用“持久化后推送”

一次聊天发送按以下顺序执行：

1. 校验会话成员身份、消息类型、长度和客户端请求 ID。
2. 在 MySQL 事务中分配会话 `seq` 并持久化消息。
3. 返回或推送发送确认 `chat_ack`。
4. 向在线会话成员推送 `chat_message`。
5. 离线或投递失败的客户端通过 `im_sync` 从持久化消息补齐。

`client_message_id` 在发送人和会话范围内唯一，用于网络重试幂等；服务端重复收到同一请求时返回原消息，不重复写入或广播。

### 4.5 多人行动采用“抢占 → 推理 → 提交”

多人模式不能沿用单人模式的自由行动语义。每次行动分三步：

1. Redis Lua 原子校验房间状态、运行态世代、当前回合、当前行动者和请求 UUID，并抢占本回合行动权。
2. 调用 Python AI，向全房间广播带 `request_id` 的流式叙事。
3. AI 完成后原子提交状态、推进回合、释放抢占并广播完成事件；失败时释放抢占并广播错误。

暂停、读档、结束或超时会轮换世代，使旧行动结果无法提交到新时间线。

## 5. 数据模型草案

迁移编号从当前 `009` 之后顺延。以下仅定义职责，具体字段长度和 SQL 在 M2.0 评审后冻结。

| 迁移 | 数据表或变更 | 核心字段 | 必要业务索引 |
|---|---|---|---|
| `010` | `friendships` | 双方规范化 ID、申请人、状态、响应时间 | 双方组合唯一；按任一用户与状态查询 |
| `011` | `conversations` | 类型、群组 ID、最后消息 seq、更新时间 | 群组会话唯一；按更新时间排序 |
| `012` | `conversation_members` | 会话 ID、用户 ID、最后读取 seq、加入时间 | 会话成员唯一；按用户列会话 |
| `013` | `messages` | 会话 ID、seq、发送人、客户端请求 ID、类型、正文、元数据 | 会话 seq 唯一；发送幂等唯一；历史分页 |
| `014` | `groups` | 名称、头像、所有者、版本、创建时间 | 按所有者查询 |
| `015` | `group_members` | 群组 ID、用户 ID、角色、加入时间 | 群成员唯一；按用户列群组 |
| `016` | 扩展 `game_rooms` | 房间码、回合时限、房间版本 | 房间码唯一；房主房间列表 |
| `017` | 扩展 `room_players` | 成员状态、离开时间 | 角色占用唯一；成员列表与状态查询 |

补充约束：

- 好友双方用 `user_low_id = min(a,b)`、`user_high_id = max(a,b)` 保存，避免 A→B 与 B→A 两条关系。
- 私聊会话同样以规范化双方 ID 保证唯一，重复打开会话返回已有 ID。
- 群聊与群组一一对应；创建群组、群主成员和群会话在同一事务完成。
- 软删除数据默认不复用原唯一键，确需重新申请或重新加入时更新原记录状态。
- 所有关联删除都通过显式事务和幂等清理方法完成，不依赖级联删除。

## 6. REST API 草案

### 6.1 用户与好友

| 方法 | 路径 | 用途 |
|---|---|---|
| `GET` | `/api/v1/users/search?keyword=` | 按精确 ID、用户名或昵称前缀查找用户 |
| `POST` | `/api/v1/friend-requests` | 发送好友申请 |
| `GET` | `/api/v1/friend-requests?direction=&status=` | 查询收到或发出的申请 |
| `POST` | `/api/v1/friend-requests/{requestId}/accept` | 接受申请 |
| `POST` | `/api/v1/friend-requests/{requestId}/reject` | 拒绝申请 |
| `GET` | `/api/v1/friends` | 好友列表和在线状态 |
| `DELETE` | `/api/v1/friends/{friendUserId}` | 双向解除好友关系 |

### 6.2 会话与消息

| 方法 | 路径 | 用途 |
|---|---|---|
| `POST` | `/api/v1/conversations/direct` | 获取或创建好友私聊会话 |
| `GET` | `/api/v1/conversations` | 当前用户会话列表 |
| `GET` | `/api/v1/conversations/{conversationId}/messages` | 按 `before_seq` 游标拉取历史消息 |
| `POST` | `/api/v1/conversations/{conversationId}/read` | 更新最后读取 seq |

### 6.3 群组

| 方法 | 路径 | 用途 |
|---|---|---|
| `POST` | `/api/v1/groups` | 创建群组 |
| `GET` | `/api/v1/groups/{groupId}` | 群详情和成员列表 |
| `PATCH` | `/api/v1/groups/{groupId}` | 修改群名称或头像 |
| `POST` | `/api/v1/groups/{groupId}/members` | 邀请好友入群 |
| `DELETE` | `/api/v1/groups/{groupId}/members/{userId}` | 移除成员或主动退群 |
| `POST` | `/api/v1/groups/{groupId}/transfer` | 转让群主 |

### 6.4 多人房间

| 方法 | 路径 | 用途 |
|---|---|---|
| `POST` | `/api/v1/rooms` | 创建多人房间 |
| `GET` | `/api/v1/rooms/{roomId}` | 获取大厅和成员状态 |
| `POST` | `/api/v1/rooms/join` | 使用房间码加入 |
| `POST` | `/api/v1/rooms/{roomId}/leave` | 离开房间 |
| `POST` | `/api/v1/rooms/{roomId}/character` | 选择或更换角色 |
| `POST` | `/api/v1/rooms/{roomId}/ready` | 设置准备状态 |
| `POST` | `/api/v1/rooms/{roomId}/start` | 房主开始游戏 |

房间开始后的行动、存档、读档、暂停、恢复和结束继续复用 `/api/v1/games/{roomId}/*`，通过 `is_solo` 分派单人或多人规则，避免创建重复资源路径。

## 7. WebSocket 契约草案

### 7.1 IM 通道

客户端消息：

- `chat_message`：`client_message_id`、`conversation_id`、`message_type`、`content`、`metadata`。
- `im_sync`：`conversation_id`、`since_seq`、`limit`。
- `ping`：心跳。

服务端消息：

- `chat_ack`：发送请求对应的持久化消息 ID 和 seq。
- `chat_message`：完整消息体。
- `im_sync_batch`：按 seq 有序的补推消息和下一水位。
- `presence`：好友在线状态变化。
- `conversation_updated`：会话摘要、未读数或群信息变化。
- `error`：稳定错误码、消息和请求 ID。

### 7.2 游戏通道新增事件

- `room_member_joined`、`room_member_left`。
- `room_ready_changed`、`room_character_selected`。
- `game_started`。
- `turn_start`：当前玩家、回合号、截止时间。
- `turn_skip`：超时或主动跳过原因。
- 复用 `narrative_chunk`、`narrative_complete`、`dice_roll`、`status_update`、`sync_batch` 和 `error`。

## 9. 测试与验收标准

- 所有 Service 权限判断、状态迁移和幂等分支有单元测试。
- 好友双向申请、重复接受、同时申请和删除重加均保持一条规范关系。
- 同一 `client_message_id` 重试不产生重复消息或 seq。
- 历史分页和断线补推不丢失、不重复、按会话 seq 有序。
- 同一通道重复连接时，新连接接管旧连接；旧连接关闭事件不能覆盖新连接的在线状态。
- 同一客户端的 IM 和游戏连接可以并存，presence 能正确区分在线与游戏中。
- 群成员变更与消息权限在同一事务边界内生效。
- 多人房间满员、重复加入、重复选角、非房主开局和非当前玩家行动均被拒绝。
- 并发行动、暂停、读档和超时竞争下只允许一个权威结果推进回合。
- Phase 1 单人游戏测试继续全部通过，旧存档 V1 可读取。
- 新 REST 路由与 OpenAPI 契约一致，CI 全部通过。
- 真实环境至少使用 3 个账号完成私聊、群聊和 3 人跑团全链路验收。

## 10. 风险与控制

| 风险 | 控制措施 |
|---|---|
| IM 与游戏事件混用导致协议复杂 | 分离 WS 入口，共享底层工具而非业务状态 |
| 多实例下进程内 Hub 无法互通 | 预留 `RealtimeBus` 接口，M2.5 验收前接入 Redis Pub/Sub |
| 消息持久化成功但推送失败 | MySQL 为权威，客户端按 seq 补推 |
| 群成员或好友删除后仍可发消息 | 每次写消息前校验当前成员关系，不只依赖连接时鉴权 |
| 多人 AI 调用期间发生暂停或读档 | 行动抢占和运行态世代共同校验，旧结果禁止提交 |
| 多人快照破坏单人存档 | 新增 V2 结构并保留 V1 解码与回归测试 |
| 无外键导致孤儿数据 | Service 显式事务、删除清理测试和定期一致性检查脚本 |

## 11. 已确认的产品决策

以下决策已于 2026-09-08 由开发者确认，M2.0 及后续实现以此为准：

1. 多人房间容纳 4—6 名真人玩家，AI GM 不计入人数。
2. 用户 ID、用户名采用精确搜索；昵称仅支持前缀搜索并限制返回数量。
3. Phase 2 首版不支持同账号多设备同时在线；同一通道的新连接接管旧连接。
4. AI 用户入群是 M2.3 独立可选块，不阻塞真人群聊交付。
5. Redis Pub/Sub 跨实例广播是 Phase 2 最终验收条件，在单实例功能稳定后实现。
